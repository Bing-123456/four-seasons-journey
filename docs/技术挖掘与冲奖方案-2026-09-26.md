# 技术挖掘与冲奖方案

2026-09-26 · 基于对当前代码库（0.8.0）的逐文件审查 + 赛事官方材料（附件 1 规则 / 附件 2 大纲）交叉分析。

---

## 0. 一句话结论

**现在的问题不是「AI 用得少」，而是「没有一个 AI 组件是你们自己训出来的」。**

全项目 11 个 AI 接口，100% 是 API 调用——DeepSeek 出文字、Qwen-VL 看图、DashScope 出图和语音。工程完成度很高，但**评委看到的是「会调 API 的团队」，不是「有算法能力的团队」**。而官方附件 2 第 3 页的附录清单里，明确要求提供「**关键算法代码、模型文件及相关说明文档**」。

创新性 25 分 + AI 技术应用 20 分，这 45 分的天花板，卡在这里。

好消息是：你们手上已经有**学生团队里极罕见的东西**——一条严格的有源证据链、一个带冻结测试集的评测脚本、一张实测出来的基线对照表。所以正确的动作不是「再加功能」，而是**把已有的严谨转成训练出来的模型，并量出增益**。

## 1. 先读评分表：创新性 25 分要什么

| 档位 | 原文 | 分值 |
|---|---|---|
| 最高档 | 提出**全新的 AI 应用模式或解决方案**，具有**开创性** | 18–25 |
| 中档 | 在现有基础上进行**显著改进**，形成独特方案 | 9–17 |
| 低档 | 创新程度较低 | 0–8 |

「用 RAG 做文化问答」是 2023 年就成熟的范式。**做得再扎实，也是中档。** 要进 18–25，必须给出一个别人没这么做的**应用模式**，而不是更好的实现。

AI 技术应用 20 分最高档的要求是「**技术实现难度高且效果好**」——注意「难度高」是硬指标，调 API 不构成难度。

附件 2 的三处硬要求也值得对照：

- 第 2 页：区分「**自行研发**的软硬产品/系统」与「**运用第三方 AI 工具**」两条路径——你们的材料现在完全落在第二条
- 第 3 页 附录 1：**原始数据、处理后的数据及数据来源说明**
- 第 3 页 附录 2：**关键算法代码、模型文件及相关说明文档**
- 第 3 页 附录 3：**参考文献**

结论：**需要一个（最好两个）自训练模型，配数据集卡、训练日志、独立测试集和模型卡。** 这一组证据同时喂三栏分数。

### 2.2 被低估的「硬工程」资产（都没进 AI 叙事）

| 资产 | 位置 | 为什么算技术含量 |
|---|---|---|
| **自研原生 WebGL 渲染器** | `components/heritage-viewer/renderer.js`(192 行) + `grain-mill.js`(128 行) | 程序化生成石磨盘几何，不用 three.js、不用 DOM，适配小程序原生 canvas。**这是真代码，不是调 API** |
| **零依赖服务端** | `server/`（运行时只依赖 `ws`） | 手写路由、任务队列、限流、鉴权、artifact 持久化，无框架无 ORM |
| **异步任务编排** | `server/tasks.js`(14KB) + `place-recommend.js` | 指纹去重、TTL 清理、并发闸门、重试上限、幂等重试、供应商链接不外泄 |
| **证据链治理** | `data/catalog.js` 31 条 fact + `dataVersion` + 来源 ID | 每条事实带来源、核查时间；这是「AI 辅助建库」的骨架 |
| **评测闭环** | `scripts/evaluate-retrieval.js` + `evaluation/culture-seed.json` | 带 dev/evaluation 冻结划分、如实标注 `modelTraining: false` |
| **三层双语架构** | `lib/i18n.js`（94KB / 1100+ 词条） | 界面词 / 名词 / 长文分层，架构上是对的 |
| **测试规模** | 43 个测试文件 / 374 处 `test()` | 「对照测试」评分项的证据 |

**这些是能拿分的，但现在一个字都没往技术报告里写。**

### 2.3 三个硬缺口

**缺口一：没有自训练模型。** 全库搜不到任何 `.pt` / `.onnx` / 模型卡 / 训练脚本 / 标注规范。附录 2 直接空着。

**缺口二：核心判断全靠手写正则。**

- `data/fruit-scope.js`（8.4KB）：越界判定
- `lib/evidence.js`：13 个 subject 正则 + 21 个 intent 正则

这两处承担了「该不该答、答什么方向」的全部决策。**评委一眼能看穿这是规则不是模型**——而这恰好是最好替换、最好量化的地方（评测脚本已经在了）。

**缺口三：检索是纯词法 BM25，零语义。** 没有 embedding、没有向量、没有重排。在 2026 年的 AI 赛场上，这是最刺眼的「技术代差」。

### 2.4 两个必须知道的硬约束

**约束一：主包只剩 13 KB。**

```
主包 2,083,624 B / 上限 2,097,152 B  →  余量 13,528 B
分包 1,509,774 B
```

微信规则：主包 ≤ 2MB、**单个分包 ≤ 2MB**、所有分包合计 ≤ 20MB。所以**端侧模型不能靠"塞进包"解决**，只有两条路：

1. 运行时 `wx.downloadFile` 下载权重 → 存本地 → 纯 JS 推理
2. 权重做成 JSON 常量放主包（只能极小，几百 KB 级）

**约束二：数据量是最大风险。**

| 资产 | 规模 | 问题 |
|---|---|---|
| 文化事实 | **31 条** | 训不出东西 |
| 评测 query | **32 条**（10 dev / 22 evaluation） | 评委一定质疑样本量 |
| 答题题库 | **6 道** | 无法做任何学习建模 |

**扩数据不是「准备工作」，它本身就是可展示的成果之一。** 而且这件事必须 Bing 参与（资料研究），不能你一个人扛。

## 3. 六个可挖掘方向

按「性价比 = 分数增益 ÷ 剩余 19 天成本」排序。

### 方向一：引用支持验证器 ★★★ 首推

**做什么。** 现在系统只能保证「答案里的每个事实 ID 都存在」——但**引用存在 ≠ 引用支持结论**。你们自己的规划文档第 7.5 节就写了这句：「有引用不等于引用正确，这要作为测试项目」。

把它做成一个**独立训练、独立评测的二/三分类模型**：

```
输入：(断言 claim, 被引证据片段 evidence, 可选上下文)
输出：直接支持 / 部分相关 / 不支持
部署：作为生成链路的硬闸门——验证不通过的句子被拦截或改写
```

**技术含量在哪。**

- 这是一个有明确学术对应的问题：**Attribution / Faithfulness / 中文 NLI**，有文献可引
- 数据集要自己建：正例来自 31 条现有 fact 的 (断言, 证据) 对，负例靠「同作物异地区 / 同地区异年代 / 相似非遗名称」构造**难负例**——这正好是你们规划 8.2 节写的标注方法
- 基座建议 `BAAI/bge-reranker-v2-m3`（多语言 CrossEncoder）或 `bge-small-zh-v1.5`，做领域监督微调

**可量化指标。**

| 指标 | 说明 |
|---|---|
| 判定准确率 / 宏 F1 | 三分类 |
| **与人工标注的一致率（Cohen's κ）** | 证明标签可靠，不是自说自话 |
| **引用错误拦截率** | 喂入故意错配的引用，看拦下多少 |
| 误拦率 | 好引用被误杀的比例——必须同时报，否则不可信 |
| 与 LLM-as-judge 的对照 | 证明「小模型够用，不必每次调大模型」 |

**为什么它是最优解。**

1. **一次标注，两个模型。** (query, evidence, 相关性) 这批标签**同时**能训「检索重排器」（你们规划里的阶段 A）和「引用验证器」。这是成本上最划算的一步。
2. **它把「可信」从 prompt 里的一句话，变成可测量、可拦截的工程属性。** 这是能进 18–25 分档的叙事——大多数 RAG 系统默认引用就是对的，你们把这个假设本身做成了模型。
3. 直接命中官方评分表「提取审核流程」和「失效处理」两项，而且是**模型级**回答。
4. 已有基建全都能复用：评测脚本、冻结划分、数据版本号、`sourceIds` 链。

**成本。** 标注 300–500 对（AI 辅助起草 + 人工复核）约 2–4 人日；训练 + 评测 2–3 天；接入 1–2 天。

**风险。** 31 条 fact 撑不起正例多样性。**必须先把 fact 扩到 80–120 条**，否则模型学到的只是 31 个模板。

---

### 方向二：端侧文化理解小模型 + 离线问答 ★★★

**做什么。** 把 `fruit-scope.js` 的越界判定和 `evidence.js` 的 subject/intent 分类，从**手写正则换成自训练的小模型**，部署到端侧。

**技术含量在哪。**

- 训练一个小型中文文本分类器：字符 n-gram + 逻辑回归 / 小型 MLP / 蒸馏后的微型 Transformer
- **真正的难点在部署**：主包只剩 13KB，所以要走「权重运行时下载 + 纯 JS 推理」，或者用 `WXWebAssembly`。**「在微信小程序的 2MB 约束下部署端侧模型」本身就是一个可讲的技术贡献**
- 端侧跑通后，配合本地 BM25 语料，**断网也能问答**

**可量化指标。**

| 指标 | 说明 |
|---|---|
| 意图分类准确率：**正则基线 vs 模型** | 对照表直接多一列，现有脚本就能测 |
| 越界判定：准确率 / 误拒率 | 现有评测已有「误拒率 7.1%」这个基线数字 |
| 模型体积（KB）/ 单次推理延迟（ms） | 端侧部署的硬指标 |
| **离线可用率** | 拔网线后仍能正确回答的比例 |

**为什么值得做。**

1. **收益可量化且基线已就位**——你们已经有一张「BM25 vs BM25+门控」的表，再加一行就是三档对照，这正是评分表要的「对照测试」。
2. **演示冲击力极强。** 答辩现场拔网线，问答照常工作——这个画面比任何 PPT 都有说服力。
3. **隐私叙事**：用户的提问不离开设备。
4. 成本可控：分类任务的数据可以用现有正则**自动生成弱标签**再人工抽检，标注成本远低于方向一。

**成本。** 弱标签生成 + 抽检 1–2 天；训练 1 天；端侧部署调试 2–3 天（这块最容易超时）。

**风险。** `WXWebAssembly` 在小程序里的支持有限且坑多。**建议先用纯 JS 推理打通（分类模型不需要 WASM），把 WASM 当加分项而不是前提。**

### 方向三：领域检索重排器 ★★（已规划，缺执行）

规划文档 8.2 节已经写得很完整了，这里只补三条**从代码里读出来的、可以立刻用上的东西**：

**（1）缺口已经量化好了，而且很小——这既是好消息也是坏消息。**

```
BM25 词法 top3            hit@1 0.714  hit@3 1.000  MRR 0.845  拒答召回 0.000  误拒 0.000
BM25 + subject/intent 门控 hit@1 0.857  hit@3 0.857  MRR 0.857  拒答召回 1.000  误拒 0.071
```

门控把「该拒答的都拒住」从 0 提到 1.0，代价是 hit@3 掉 0.143。**重排器要补的就是这 0.143。**

但注意：**样本只有 22 条冻结集**。hit@3 从 1.000 掉到 0.857 = 14 条里错了 2 条。**2 条样本的差异不足以支撑任何训练决策。** 所以——

**（2）第一件事不是训练，是扩评测集。** 扩到 150–300 条冻结样本，再重跑这张表。否则你训出来的模型即使「提升」了，也是噪声。这一步零风险、半天到一天，而且**顺便把「样本量太小」这个评审质疑点堵上**。

**（3）重排器的训练数据和方向一的验证器同源。** 把标注一次做两用：`(query, evidence, 相关性)` 训重排；`(claim, evidence, 蕴含)` 训验证。**同一批标注工作，两个模型，两份指标。** 这是这次技术升级里最划算的一笔。

### 方向四：知识追踪驱动的自适应文化学习 ★★

**做什么。** 三个游戏（识果 / 答题 / 绘画）现在完全无 AI、无数据、无个性化。答题只有 6 道、固定顺序、答完即止。

升级为**知识追踪**：建模用户对「节气 / 农具 / 非遗 / 作物史 / 世界风物」各知识维度的掌握度，然后：

- 自适应选题（挑「最薄弱且信息量最大」的下一题）
- 驱动内容推荐（哪类文化内容推给谁）
- 给用户一张「文化掌握度画像」

**技术含量在哪。**

- 可选模型有清晰文献路径：**IRT**（项目反应理论）、**BKT**（贝叶斯知识追踪）、或轻量 **DKT**
- 这是经典心理测量 + 教育数据挖掘问题，引用成本低，评审认可度高
- 和规划文档里的「阶段 B：个性化体验排序」是同一条线，可以合并叙事

**可量化指标。** **下一题正确率预测的 AUC**、与固定顺序基线的对照、学习完成率、推荐命中率。

**成本与风险。** **题库 6 道是致命瓶颈**——必须扩到 60–100 道。好消息是扩题可以复用方向一的「AI 起草 + 人工审核」流程，一次建两样东西。

**建议**：如果 10/8 前扩题来不及，就把这个降级为「已设计、待数据」，别硬上。**IRT 的公式可以写进报告，但不要声称跑出了结果。**

### 方向五：跨模态「以图问文化」 ★

**做什么。** 现在识果是孤立的一次 VLM 调用：图片 → 品种名，然后结束。没有评测、没有拒识、没有和知识库联动。

升级为：图片 → VLM 抽取**结构化视觉证据**（果形 / 色泽 / 纹理 / 成熟度 / 场景 / 器物）→ 跨模态检索文化库 → 回答「这是什么，以及它在河南农耕文化里意味着什么」。

**自研点在哪。** 建一个**识果 Top-k 评测集 + 拒识机制**。现在连「识果准不准」都没数据，这在评分表的「应用成效」栏是明显缺口。

**指标。** Top-1 / Top-5 准确率、拒识率、跨模态检索 MRR、与纯文本检索的对照。

**成本。** 需要拍/收集标注图，成本中等。**优先级放在前四个之后。**

---

### 方向六：术语约束的双语文化翻译 ★★（低成本高贴题）

**做什么。** 你们有 1100+ 词条词典 + 长文按需 AI 翻译。但 AI 翻文化专名会漂移——瓜豆酱、裴李岗、仰韶、大河村、二十四节气、GIAHS……

升级为**术语约束翻译**：

1. 建术语表（中文专名 → 英文规范译名），翻译时强制注入
2. **后置校验器**：检测译文中术语是否漂移、是否漏译，漂移则重译或标红
3. 对照实验：无约束翻译 vs 术语约束翻译

**技术含量在哪。** 「专名一致性」是文化翻译最硬的难点，也是有明确评测方式的问题。可以做**术语一致性自动评分**（术语命中率、漂移率），这本身就是一个可复用的评测器。

**指标。** 术语一致率、漂移率、人工双盲评分、与无约束翻译的对照。

**为什么性价比高。**

- **文化出海是这条赛道最真实的落地价值**，评审天然买账
- 你们的双语架构已经做好了，加一层术语约束是增量改造，不是重写
- 成本低（1–2 天），不依赖 GPU
- 与前面几个方向完全解耦，可以独立推进——**适合作为「保底成果」**

## 4. 推荐组合：一条能讲通的主线

不要平铺六个方向。串成一条主线：

> ### 我们做的不是「让模型讲文化」，而是「让 AI 参与文化知识的生产，且每一句都可审计」。

```
原始文献
   ↓  ① 抽取模型（LLM + schema 约束）产出候选 (实体, 关系, 证据片段)
   ↓  ② 引用支持验证器（★自训练）判定「这段原文是否真的支持这条断言」
   ↓  ③ 冲突检测（新事实 vs 已有事实库，同实体同属性是否矛盾）
   ↓  ④ 人工审核 → 入库（带完整审计轨迹：来源 / 抽取模型版本 / 审核人 / 时间）
   ↓  ⑤ 检索（BM25 → + 领域重排器（★自训练））
   ↓  ⑥ 生成（模型无写事实权限，只能选证据 ID）
   ↓  ⑦ 引用校验（★自训练，与 ② 同源）→ 不通过则拦截 / 改写
   ↓  ⑧ 端侧兜底（★自训练意图模型 + 本地语料，断网可用）
```

**三个自训练模型**：抽取、验证/重排、意图门控。
**一条审计链**：每条文化事实从原始文献到最终输出的每一步都可追溯。
**一个诚实边界**：模型无写事实权限，所以幻觉在结构上不可能发生。

这条主线的好处：

- **同时喂三栏分数**：创新性（新的知识生产模式）、AI 技术应用（自训练模型 + 难度）、应用成效（可测量指标 + 真实数据）
- **每一项都有对照基线**，不是自说自话
- **诚实**——训练没完成就写「拟训练」，这反而加分（你们规划文档里已经建立了这个调性，保持住）

## 6. 红线

这几条如果破了，前面所有努力都会反噬：

1. **不写「自训大模型」。** 训的是**基于开源基座的领域微调小模型**，基座名称和许可证必须写明。
2. **不把合成数据当真实用户数据。** 合成实验就标「合成数据实验」，不做任何泛化声明。
3. **不在冻结测试集上调参。** 冻结就是冻结，调了就失去公信力。接入门槛要在看结果**之前**登记。
4. **不隐藏负结果。** 如果微调后 nDCG@5 没提升，如实写——「我们验证了领域微调在这个数据规模下无稳定增益」本身就是一个有价值的发现，比造假强得多。
5. **样本量不达标就不下结论。** 22 条冻结集上 2 条样本的差异不能当结论。先扩样本，再谈提升。
6. **不用 API 调用冒充算法能力。** 「自研产品/系统」和「运用第三方 AI 工具」两条路径要在报告里分清，混着写会掉分。

## 7. 最后一句

你们现在缺的不是功能，也不是工程能力——**`withFallback` 那套降级体系、任务队列的幂等设计、证据链治理，这些做得比多数参赛队伍都扎实。**

缺的是**把这份严谨变成可测量的模型增益**。

一件事如果只能这么讲——「我们用了 DeepSeek 做问答」——那它拿不到高分。如果能这么讲——「我们建了 N 条标注的文化证据数据集，训了两个领域模型，在独立冻结测试集上引用错误拦截率 X%、误拦率 Y%，并如实报告了一处未达预期的结果」——那才是特等奖的料。
