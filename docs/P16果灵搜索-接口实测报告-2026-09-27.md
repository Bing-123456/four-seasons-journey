# P16「果灵搜索」接口实测报告

2026-09-27 · 测试对象：`miniprogram/pages/search/search.js`（P16）

---

## 0. 结论摘要

跑了 **74 个查询**，覆盖 11 组场景。**正常路径输出质量很高**——结构清晰、内容有出处、口径克制。

但发现 **8 个缺陷，其中 3 个是「答错」级别**：用户问 A，系统答 B。

| 级别 | 数量 | 代表案例 |
|---|---|---|
| 答错（用户问 A 得到 B） | 3 类 | 搜「凤梨」得到**梨**的内容；搜「番石榴」得到**石榴**；搜「日本的柿子」得到**河南柿子** |
| 输出异常（重复/文案荒谬） | 3 类 | 搜「甘蔗」得到 3 份相同内容 + 「甘蔗 与 甘蔗 与 甘蔗的关键差别」 |
| 检索失效（该命中没命中） | 2 类 | 英文输入 0 命中；「为什么谷雨前后种瓜点豆」查不到 |

**先说一个重要的架构事实**：P16 **完全不调用 `/api/ask`**，是纯本地检索。

```
search.js 中 '/api/ask' 出现 0 次，'answerQuestion' 出现 0 次，'evidence' 出现 0 次
service 仅出现 1 次 —— 用于「EN 按钮」的按需翻译
```

⚠️ 这一点与协作文档「待确认清单 Q6」的描述不符。Q6 写的是「P16 检索走本地文化库，`/api/ask` 仅在开启云端时增强证据排序」——**实际上 P16 根本没有云端增强路径**，`service.answerQuestion` 是给别的页面用的。Q6 需要更正。

## 1. 搜索链路长什么样

`finishSearch(question)` 的实际分支顺序：

```
matchFruits(question)                       ← 纯子串匹配水果名
  ├─ 命中 → composeAnswer()                 ← 直接出答案卡
  │        【农谚与时令】【乡土食养与习俗】【拓展科普】(+【一句话对比】)
  │        + 相关农谚(≤3) + 节气札(≤2)
  └─ 未命中 → fruitScope.classify(question) ← 只有这里才判边界
              ├─ scope='out' → 婉拒话术
              └─ 其他      → 农谚模糊匹配（取问题前 4 字）
                             ├─ 命中 → 只显示农谚
                             └─ 未命中 → 「没找到相关水果」
```

素材库规模：

| 项 | 数量 |
|---|---|
| 四季条目 | **48**（春 11 / 夏 13 / 秋 13 / 冬 11） |
| 不重名水果 | **42** |
| 每条的固定分类 | **6 个**（folk / history / craft / story / tools / health） |
| 农谚 | 5 条 |
| 节气札 | 24 条 |

## 2. 正常路径的实际输出（质量不错）

### 2.1 单果名 → 三段卡

搜「**柿子**」：

```
【农谚与时令】柿子以鲜果和柿饼两种面貌进入秋日生活。农谚"七月核桃八月梨，九月柿子乱赶集。"…
【乡土食养与习俗】柿饼的水分比鲜柿少，甜味更集中，吃一小份与吃同体积鲜果并不相同…
【拓展科普】柿树是落叶果树，果实顶端持存的萼片是容易辨认的特征…
+ 农谚 1 条、节气札 2 条
```

口径克制、有出处、明确区分「鲜果 / 柿饼」——**这是这套系统的强项**。

### 2.2 对比问法 → 多一段「一句话对比」

搜「**李子和杏子有什么区别**」→ 匹配 `李子 + 杏`，输出 4 段（3 段内容 + 对比段）。

### 2.3 境外果品 → 婉拒 + 引导

| 查询 | scope | 输出 |
|---|---|---|
| 榴莲 | out:榴莲 | 「榴莲为外来引进我国的果品…可以试试《四时》收录的荔枝、龙眼、黄皮。」 |
| 车厘子 | out:车厘子 | 「…可以试试…樱桃。」 |
| 蓝莓 | out:蓝莓 | 「…可以试试…桑葚、杨梅。」 |
| 牛油果 | out:牛油果 | 「…可以试试…无花果、木瓜。」 |
| 莲雾 | out:莲雾 | 「…可以试试…杨桃、山竹。」 |
| 红毛丹 | out:红毛丹 | 「…可以试试…荔枝、龙眼。」 |

**婉拒不生硬，还给了替代路径**——这个设计是对的。

### 2.4 完全无关的问题 → 统一兜底

「你好」「今天天气怎么样」「怎么做红烧肉」「河南有什么好玩的地方」→ 全部返回同一句：
> 没找到相关水果，换个关键词试试，比如：青梅、西瓜、柿子。

## 3. 缺陷清单

### 🔴 P0-1：子串匹配导致答错（7 组碰撞）

`matchFruits` 用的是最朴素的 `question.indexOf(name) !== -1`，没有词边界、没有最长优先。

对全部 42 个水果名逐个搜索，**7 个名字会撞车**：

| 搜索词 | 实际匹配 | 原因 |
|---|---|---|
| **杨梅** | 青梅 **+** 杨梅 | 青梅的别名「梅」是「杨梅」的子串 |
| **冬枣** | 枣 **+** 冬枣 **+** 冬枣 | 「枣」是独立水果名 |
| **椰枣** | 枣 **+** 椰枣 | 同上 |
| **甘蔗** | 甘蔗 ×3 | 春/秋/冬三季各有一条 |
| **葡萄** | 葡萄 ×2 | 夏/秋各一条 |
| **柚子** | 柚子 ×2 | 秋/冬各一条 |
| **脐橙** | 脐橙 ×2 | 秋/冬各一条 |

### 🔴 P0-2：**凤梨 → 秋梨**（最荒诞的一个）

别名表里 `秋梨` 注册了别名「梨」。于是：

| 输入 | 匹配 | 问题 |
|---|---|---|
| **凤梨** | **秋梨** | 凤梨是菠萝的别名，系统给的是**梨**的内容 |
| 西梅 | 青梅 | 西梅是境外果品，却答了青梅 |
| 腊梅 | 青梅 | — |
| 梨子 | 秋梨 | 合理 |

而菠萝条目正文里明明写着「**菠萝也称凤梨**」。**用户搜凤梨，拿到的是梨的农谚和食养**——这是最容易被评委或用户当场撞见的错。

### 🔴 P0-3：边界判定被绕过（设计意图与实现相反）

`fruit-scope.js` 的注释专门写了防误判逻辑：

> 只剩境外水果名：先摘掉它，避免「番石榴 / 葡萄柚」里的「石榴 / 葡萄」被误判成《四时》收录对象。

`classify()` 确实正确返回了 `scope='out'`。**但 P16 的调用顺序把它绕过去了**——`finishSearch` 先跑 `matchFruits`，命中就直接出答案，`classify` 根本没机会执行。

| 查询 | scope 判定 | 实际输出 | 应该是 |
|---|---|---|---|
| **番石榴** | `out:番石榴` | 石榴的完整答案卡 | 婉拒 |
| **葡萄柚** | `out:葡萄柚` | 葡萄的完整答案卡 | 婉拒 |
| **西梅** | `out:西梅` | 青梅的完整答案卡 | 婉拒 |
| **日本的柿子** | `out:日本` | 柿子的完整答案卡 | 婉拒 |

「日本的柿子」尤其严重：`classify` 明确判为「境外农耕文化，不收录」，但用户仍然拿到了**河南柿子**的内容——**答非所问，且违反了内容边界策略**。

### 🟠 P1-1：跨季同名水果 → 重复内容 + 荒谬文案

`compare = fruits.length >= 2` 用的是**匹配条目数**，不是**不同水果数**。所以：

| 查询 | 输出的对比文案 |
|---|---|
| 甘蔗 | 「**甘蔗 与 甘蔗 与 甘蔗**的关键差别见上方各段；**两者**成熟时节…都不同。」 |
| 葡萄 | 「葡萄 与 葡萄的关键差别见上方各段；两者…」 |
| 柚子 | 「柚子 与 柚子的关键差别见上方各段；两者…」 |
| 冬枣 | 「枣 与 冬枣 与 冬枣的关键差别见上方各段；两者…」 |

三个「甘蔗」还写「两者」。而且**用户只搜了一个词，却得到了对比卡片**。

同时三段正文也重复了（「葡萄」输出 2 行 ×3 段 = 6 行，内容几乎一样）。

### 🟠 P1-2：「河南能种蓝莓吗」不给婉拒话术

| 查询 | scope | 实际输出 | 问题 |
|---|---|---|---|
| **河南能种蓝莓吗** | `mixed`（含国内标记「河南」） | 「没找到相关水果，换个关键词试试，比如：青梅、西瓜、柿子。」 | 蓝莓是**明确的不收录对象**，但 `mixed` 分支直接跳过了婉拒话术，用户看到的是"没找到" |

对比「蓝莓」（无国内标记）→ 正确婉拒。**加个"河南"反而降级成了无效提示**。

### 🟠 P1-3：农谚模糊匹配取「前 4 字」，极其脆弱

`question.slice(0, 4)` 做子串匹配：

| 查询 | 取前 4 字 | 命中 |
|---|---|---|
| 谷雨前后种瓜点豆 | 谷雨前后 | ✅ 1 条 |
| 谷雨前后种瓜点豆是什么意思 | 谷雨前后 | ✅ 1 条 |
| **为什么谷雨前后种瓜点豆** | **为什么谷** | ❌ **0 条** |

**同一个问题，加个「为什么」就查不到了。** 这是启发式取前缀的必然结果——问句的真实意图词不在开头。

### 🟡 P2-1：英文输入完全无法匹配

`matchFruits` 只匹配中文名（`fruit.name`）。而 P16 是**支持英文界面的**（`i18n` 有 `fruit_<id>` 词典层）。

| 输入 | 命中 |
|---|---|
| loquat / watermelon / plum / persimmon | **全部 0** |

英文模式下搜英文水果名 → 必然「没找到相关水果」。**界面翻译了，检索没翻译**。

### 🟡 P2-2：测试覆盖有洞，恰好绕过了所有 bug

`tests/fruit-scope.test.js` 里有这个用例：

> `the Guoling search page refuses foreign fruit and still finds world-layer fruit`

它测的是：
- `榴莲` → 婉拒 ✅
- `枇杷` → 能找到 ✅
- `不存在的问法` → 空提示 ✅

**它没测任何碰撞案例**（番石榴 / 葡萄柚 / 西梅 / 杨梅 / 冬枣 / 椰枣 / 凤梨）。

榴莲恰好**不包含任何收录水果名**，所以测试通过。**换成番石榴就会红。** 这是典型的「测试选到了不触发缺陷的样本」。

## 4. 根因

三个问题，三层：

**根因一：`indexOf` 子串匹配没有优先级概念。**
「梅」既是青梅的别名，又是杨梅的子串；「梨」既是秋梨的别名，又是凤梨的子串。**没有「最长匹配优先」和「别名只在完整词出现时生效」的规则。**

**根因二：`finishSearch` 的分支顺序与 `fruit-scope` 的设计意图相反。**
`fruit-scope.js` 假设自己先被调用（所以写了「先摘掉境外果名」的防护），但 P16 把它放在了 `matchFruits` 之后。**防护代码写了，但执行不到。**

**根因三：对比判定用「条目数」而非「不同水果数」。**
`fruits.length >= 2` 在跨季重复的场景下必然误判。

---

## 5. 修复建议（按优先级）

### 修 1：给 `matchFruits` 加「最长匹配优先 + 别名整词生效」

```
1. 先收集所有命中，按匹配到的名字长度降序排列
2. 用一个 spans 数组记录已占用区间（参照 fruit-scope.js explicitSubjects 的写法）
3. 若某命中区间被更长的命中完全覆盖 → 丢弃（杨梅 吃掉 青梅）
4. 别名（梅/梨）只在「前后都不是汉字」或「整词相等」时生效
5. 同一 name 的多个季节条目 → 按季节排序保留，但要去重（见修 3）
```

`fruit-scope.js` 里的 `explicitSubjects()` 已经有现成的区间遮蔽写法，可以直接复用。

### 修 2：把 `classify` 提到 `matchFruits` 之前

```js
const scope = fruitScope.classify(question);
if (scope.scope === 'out') { 婉拒; return; }     // 先判边界
const fruits = matchFruits(question);            // 再检索
```

这样「番石榴 / 葡萄柚 / 西梅 / 日本的柿子」会正确婉拒。**改动只有 3 行，收益最大。**

### 修 3：对比判定改用不同水果数

```js
const uniqueNames = new Set(fruits.map(h => h.fruit.name));
const compare = uniqueNames.size >= 2;
```

同时 `composeAnswer` 里按 name 去重，避免「甘蔗 ×3」重复三段正文。

### 修 4：跨季重复的处理策略

同一个水果名出现在多季（甘蔗/葡萄/柚子/脐橙/冬枣），**不应该输出 N 份内容**。建议：
- 只保留一条正文（优先匹配用户问题里出现的季节词，否则按当前季节）
- 在卡片上标注「该果物在《四时》中横跨春、秋、冬三季」，把重复变成信息

### 修 5：农谚匹配改用关键词命中，不用前缀

```js
// 现状：question.slice(0, 4)
// 建议：用农谚正文里的关键词反向匹配问题
const hits = proverbs.filter(p => p.keywords.some(k => question.includes(k)));
```
（需要在农谚数据里补 `keywords` 字段，或从 `text` 抽 2-gram 求交集。）

### 修 6：`mixed` 分支也要给边界提示

「河南能种蓝莓吗」→ 应返回：「蓝莓为外来引进我国的果品…（但问题里提到河南，如需了解河南本土果品可以…）」

### 修 7：英文检索

`matchFruits` 增加英文名匹配：用 `i18n.dict['fruit_' + fruit.id]` 的英文值建反查表。这样英文模式才能搜到。

### 修 8：补测试

把 11 组场景里所有碰撞案例写进 `tests/fruit-scope.test.js`，作为回归用例：

```
番石榴 → 婉拒（不得出现石榴内容）
葡萄柚 → 婉拒（不得出现葡萄内容）
西梅   → 婉拒
凤梨   → 菠萝（不得出现梨内容）
杨梅   → 只出杨梅（不得出现青梅）
冬枣   → 只出冬枣（不得出现枣）
甘蔗   → 去重后单条
河南能种蓝莓吗 → 婉拒或带边界提示
```

## 7. 一句话总结

**这套搜索的内容质量是好的，坏在检索层太朴素。**

`indexOf` 子串匹配 + 分支顺序颠倒 + 用条目数判对比，三个小问题叠加，产生了「搜凤梨得到梨」「搜番石榴得到石榴」「搜日本柿子得到河南柿子」这类会被一眼看穿的错误。

**修 1 到修 3 加起来大约 30 行代码，能解决 3 个 P0 中的 3 个。** 建议优先做。
