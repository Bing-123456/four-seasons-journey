# 为什么往届获奖仓库「只有一个模型」——赛道形态澄清

- **起因**：2026-09-27，你提出「我看其他人工智能算法精英赛获奖的 github 仓库 基本都是一个算法 或者模型，根本就没有做前后端的」
- **先说结论**：
  1. **你的观察完全正确**——我实测了手上的 33 个往届仓库，**32 个是纯算法/模型，只有 1 个提到前后端**。
  2. **但这些仓库几乎全属于「算法挑战赛道」，不是我们在的「算法主题赛」**——那个赛道的规则**要求**交模型和提交文件，做前后端反而跑偏。
  3. **主题赛的规则正好相反**：附件 1 要求交**演示视频（展示作品功能）+ 完整代码包 + 工程文件**，评分表里 **45 分**（需求分析 + 项目实施 + 应用成效）是给「做出来的完整作品」的。
  4. **但你的担忧戳中了真问题**：不是「不该做前后端」，是「**技术点太散，没有一条主线**」。这是真正要改的地方。

## 三、算法主题赛的规则完全相反（三重官方证据）

这是关键。我们在的是**「算法主题赛 · 智能文化」（AIC-TC-002）**，规则白纸黑字不一样。

### 证据 1：附件 1《竞赛规则及作品提交要求》三、作品材料规范

要交的材料清单（原文）：

| # | 材料 | 原文要求 |
|---|---|---|
| 1 | 作品名称 | ≤20 字 |
| 2 | 作品简介 | ≤300 字，「问题-方案-效果-应用」逻辑 |
| 3 | 技术方案 | PDF，≤10M，按模板大纲 |
| 4 | **演示视频（若有）** | **MP4，3–5 分钟，清晰展示作品功能、实现流程与应用效果** |
| 5 | 答辩 PPT | PDF |
| 6 | 佐证材料 | 专利/软著/论文/合作意向书/用户反馈/试点证明 |
| 7 | **作品其他材料链接** | **将完整代码包、大型工程文件、高清图纸等大容量文件存放文件夹并上传网盘** |

**两个致命细节**：

- **「演示视频：清晰展示作品功能」**——如果作品只是一个模型，你演示什么？**主题赛默认你有一个能演示的东西。**
- **「完整代码包、**大型工程文件**、高清图纸」**——官方明确预期提交物里有「大型工程文件」。

### 证据 2：附件 1 二、作品要求（三）实用性与成熟度

> 作品须具备实际应用价值，**已在实际场景中应用并取得良好效果，展示清晰的应用案例和数据证明**，或者应具备向实际应用转化的潜力和可行性方案。

**「应用案例 + 数据证明」——一个模型交不出这个。**

### 证据 3：附件 2《技术报告参考大纲》三、AI 技术工具选择与运用

> **如果参赛团队自行研发的软硬产品或系统完成需求目标**，主要说明产品主要采用了哪些人工智能技术、开发平台或环境，产品的功能和技术指标等；**如果参赛团队运用人工智能工具完成需求目标**，需说明选择的人工智能工具名称、选型依据等。

**官方明确区分两条路径，并且都允许**：① 自研软硬产品/系统 ② 运用 AI 工具。**没有说「只交算法」。**

而且大纲四、项目实施 的 2 明确列出：

> 描述实施过程中的关键技术环节，如数据采集与处理、模型训练与优化、**系统开发与部署**等

**「系统开发与部署」被官方列为关键技术环节之一。**

### 证据 4：评分表结构（第七届附件 3 = 第八届附件 1 四，两届完全一致）

| 评分项 | 分值 | 关键细则原文 |
|---|---|---|
| 创新性 | **25** | 提出全新的 **AI 应用模式或解决方案**…在现有基础上显著改进，形成独特方案 |
| 需求分析 | **15** | 问题剖析深入全面，**需求调研方法科学** |
| AI 技术应用 | **20** | AI 技术或工具选择合理，与项目融合紧密，**技术实现难度高且效果好** |
| 项目实施 | **15** | 实施方案完整，计划合理，**关键技术实现良好** |
| 应用成效 | **15** | 成果显著，效益突出，**数据详实** |
| 总结与展望 | 10 | — |
| **附录附加分** | **+5** | 数据资料、注释详细的代码与模型、参考文献…每项 1–2 分 |

**看这个结构**：

- **只有 20 分（AI 技术应用）直接奖励「技术难度」**
- **45 分（需求分析 + 项目实施 + 应用成效）奖励「做一个解决问题的完整东西」**
- 创新性 25 分写的是「**AI 应用模式或解决方案**」——注意是**应用模式**，不是算法

**如果只交一个模型**：需求分析（无用户）、项目实施（无实施）、应用成效（无成果无数据）——**45 分直接放弃**，加上附录里「数据资料/用户反馈/试点证明」也拿不到。**天花板大概 45 分。**

> ⚠️ 注意一个细节：**「应用成效 15 分」的细则写的是「成果显著，效益突出，数据详实」**。这是我们目前最弱的一项——见 §五。

## 四、所以：赛道不同，形态就该不同

| | 算法**挑战**赛道（那 32 个仓库） | 算法**主题**赛 · 智能文化（我们） |
|---|---|---|
| 数据集 | 官方分级下发 | **不提供**（开放式赛题） |
| 排行榜 | 有，每小时刷新，占 **70%** | **没有** |
| 提交物 | **代码 + 模型文件 + 提交结果** | **技术报告 + 演示视频 + 完整代码包 + 佐证材料** |
| 评审方式 | 70% 排行榜 + 30% 答辩 | **100% 专家评审** |
| 获奖逻辑 | **一个算法做到最好** | **一条技术主线 + 一个可演示的完整载体** |
| 做前后端 | ❌ 偏题 | ✅ **必需**（要演示、要应用成效） |

**「往届获奖仓库只有一个模型」不是评审偏好的证据，是赛道规则的必然结果。** 你看到的样本 97% 来自另一个赛道。

**顺带解释一个之前的困惑**：为什么「智能文化」赛道在 GitHub 上 0 个开源仓库？——因为主题赛的代码是**上传百度网盘**提交的（附件 1 三、7），不是发 GitHub。**这是规则使然，不是没人做。**

## 五、但你的担忧是对的——真问题不在「做了前后端」

**把话说清楚**：你的观察指向的真问题是这个——

> **获奖作品的共同点是「技术点高度集中」。挑战赛道是一个算法做深；主题赛也应该是「一条技术主线做深」，而不是「十个功能做浅」。**

### 5.1 我们现在的问题：看起来很全，但记不住

盘一下现有资产：

| 层面 | 有什么 |
|---|---|
| 页面 | **29 个**（四季 / 文化 / 文物 / 行程 / 地图 / 预订 / 卖家 / 游戏 / 识果 / 绘画 / 搜索 / 学习…） |
| 后端 | **6 个任务接口**（ask / sellerInsight / identifyFruit / fruitStory / translate / profile） |
| AI 能力 | **5 种**（LLM 问答 / VLM 识果 / 图像生成 / 水墨画 / 语音朗读） |
| 数据 | 415 条结构化内容 / 31 条事实 / 14 个来源 |
| 评测 | 32 条标注 / 5 个指标 |

**问题来了**：让你用一句话说出「这个作品的技术核心是什么」——**答不上来**。

因为它是「什么都有」。而「什么都有」在评审眼里约等于「**每个都不深，每个别人都能做**」。

**这正是你在那 32 个仓库里感受到的落差**：它们只有一个点，但那个点做得很深。我们有十个点，每个点都是「调了个 API」。

### 5.2 但解决方案不是砍功能

**不要砍前后端。** 理由：主题赛的 45 分需要它，演示视频需要它，应用成效需要它。

**要改的是「组织方式」**：把散落的功能**重新叙述成一条技术主线的三层证据**。

## 六、提炼主线：把「十个功能」重组成「一条主线」

### 6.1 主线是什么

**「面向文化知识问答的可控生成架构」**——一句话：**让 AI 在文化领域只说实话，说不出就不说。**

这条主线解决的是一类真实问题，不是我们的项目特有的：**文化类内容最怕的不是答不出来，是编造出处。**

### 6.2 三层证据（现有资产重新归位）

| 层 | 技术内容 | 现有证据 | 对应评分项 |
|---|---|---|---|
| **第一层：不让模型自由作答** | 模型只从已核验证据里挑 ID，事实措辞锚定来源；证据不足直接拒答 | `server/tasks.js` 的 `// An unsupported factual question is never handed to an unconstrained LLM.` + 输出校验（ID 必在候选集、数量 1–4、`unanswerable` 必须布尔） | **AI 技术应用 20** |
| **第二层：可解释的检索** | BM25 + 意图/主语闸门，35 条规则，输出可追溯 | `lib/evidence.js`（263 行）+ `retrievalMethod: 'lexical-bm25-intent-gates'` | **AI 技术应用 20** |
| **第三层：可量化的评测** | 32 条标注（含 8 条拒答负样本）+ hit@1/hit@3/MRR/拒答召回/误拒率 | `test-results/retrieval-evaluation.json`：拒答召回 **1.000** | **创新性 25 + 应用成效 15** |
| **第四层：内容边界用代码兜底** | 35 个域外果物本地闸门拦截，不给模型编造机会 | `fruit-scope.js` + `if (task === 'fruitStory' && local.outOfScope) return local;` | **创新性 25** |
| **第五层：诚实降级** | 模型挂了就明确告诉用户，不假装 AI 在工作 | `local-fallback` / `local-template` / `local-rules` + 界面文案 | **创新性 25** |
| **加分项：自训练视觉模型** | 14 类中国本土水果细粒度识别，替换不稳定的云端 VLM | 待做（先测 VLM 基线，见另一份文档） | **AI 技术应用 20 + 附录 2** |

**这样一重组，同一个系统，叙述完全不同**：

- ❌ 改前：「我们做了一个小程序，有 29 个页面，用了 LLM 和 VLM」→ 听起来像课程作业
- ✅ 改后：「我们提出了一个**面向文化领域的可控生成架构**：通过证据锚定、意图闸门、拒答机制、内容边界兜底和诚实降级五层设计，把文化问答的幻觉率降到 X。评测集上拒答召回 1.000。该架构在 29 个页面的小程序上完成了端到端验证。」→ 听起来像研究

**技术没变，重心变了。**

### 6.3 一个必须补的短板：《应用成效》的「数据详实」

评分细则原文：「成果显著，效益突出，**数据详实**」。

我们现在**最缺的就是这个**。现有可用的数字：

| 已有 | 缺 |
|---|---|
| 415 条结构化内容、31 条事实 100% 可回溯、14 个来源 | **真实用户数 / 使用次数** |
| 32 条评测标注、拒答召回 1.000 | **试点场景 / 合作意向** |
| 29 个页面、7 个接口、392 处测试 | **效率提升幅度 / 成本降低比例** |

**建议**（按性价比排序）：
1. **实测一组「人 vs 系统」对照**：让队友人工查 20 个文化问题（查资料要多久、对不对），系统跑同一组 → 得出「**人工 X 分钟 vs 系统 Y 秒**」
2. **找 1 个真实场景做试点**：果园/博物馆/文化馆，出一张**试点证明或用户反馈**（佐证材料里明确列了这两项）
3. **记录拒答数据**：系统跑了多少次、拒答了几次 → 「**拒答率 X%，零编造**」本身就是数据

**没有数据就不要写「效果显著」。** 写「我们完成了一组对照实验，测得 X」比空写「效果显著」得分高——细则里「数据详实」四个字是硬要求。

## 七、自检：怎么判断我们是不是「十个功能做浅」

用这四个问题自检，任何一个答不上来就是危险信号：

| 自检问题 | 合格标准 |
|---|---|
| **1. 一句话技术核心是什么？** | 能说出一条主线，且这条主线**不是「用了 LLM」**（那是所有人都用的东西） |
| **2. 哪一项是「别人做不出来」的？** | 至少有一项**有量化指标 + 有对照实验**的能力 |
| **3. 如果只保留一个功能，保留哪个？** | 能立刻答出来（答不出说明没有主线） |
| **4. 去掉 AI 部分，作品还剩什么？** | 应该剩不了多少——如果剩很多，说明 AI 是贴上去的 |

**第 4 条对我们特别重要**：如果去掉 LLM/VLM 调用，小程序里还有 29 个页面的内容展示和交互——**那说明 AI 是「加」上去的，不是「长」在里面的**。这条主线的叙述方式能解决它：**把「AI 是功能之一」改成「AI 是架构核心，页面是它的验证场景」**。

## 八、一句话回答你的问题

**你看到的那些仓库没错，但它们几乎全是「算法挑战赛道」的——那个赛道的规则就是交一个模型，做前后端反而偏题。**

**我们在「算法主题赛」，规则正相反**：附件 1 要求交**演示视频（展示作品功能）+ 完整代码包 + 大型工程文件**，评分表里 **45 分**（需求分析 / 项目实施 / 应用成效）是给「做出来的完整作品」的，只有 20 分奖励纯技术难度。**只交一个模型，在主题赛里天花板大概 45 分。**

**但你的担忧是对的，只是方向要调一下**：

- ❌ 不是「不该做前后端」
- ✅ 是「**不能只有前后端，得有一条技术主线**」

**具体动作**：把现有系统重新叙述为「**面向文化知识问答的可控生成架构**」+「**29 个页面的端到端验证**」+「**自训练视觉模型**」三层，然后补上最缺的《应用成效》真实数据。

**技术没变，重心变了。** 这比再堆十个功能有用得多。
