# 消融实验：可控多模态 RAG 管线的分层收益

**日期**：2026-09-28
**评测集**：`evaluation/culture-seed.json` · `culture-seed-2026-09-28-v2` · evaluation 拆分 22 条（14 可答 + 8 不可答）
**模型**：`deepseek-flash`（temperature=0，三组同一模型、同一参数）
**脚本**：`scripts/evaluate-ablation.js`（`npm run eval:ablation`）
**原始数据**：`test-results/ablation-evaluation.json`（含全部回答原文与裁判理由）

---

## 一句话结论

**去掉检索与闸门层，同一个模型在资料库无法回答的 8 个问题里，有 2 个（25%）给出了具体的事实性结论——其中一条是一整套编造的食品发酵安全温度参数。**

这不是推测，是实测。它也是整个分层架构存在的理由。

---

## 一、实验设置

### 1.1 为什么做这个实验

只说「我们用了大模型」在评审里没有说服力。真正能说明问题的是：**把我们的层去掉，同一个模型会怎样。** 所以设三组对照，唯一变量是「模型能拿到什么资料」。

### 1.2 三组对照

| 组 | 定义 | 模型能看到什么 |
|---|---|---|
| **A 裸 LLM** | 不给任何资料，直接问模型 | 只有问题文本 |
| **D 朴素 RAG** | 把资料库全部 31 条核验事实塞进上下文，并**明确提示「资料里没有相关内容时请如实说明资料不足」** | 全部 31 条事实 |
| **C 本系统** | 本地闸门 + 模型选证（`server/tasks.js` 真实路径） | 闸门通过后筛出的 ≤4 条候选事实 |

> **D 组是刻意选的最强基线。** 通常的「朴素 RAG」基线不给拒答提示，那样赢它没有意义。这里给它和本系统同等甚至更多的资料、以及明确的诚实提示——**只有赢过这个基线，闸门层才真正站得住**。

### 1.3 指标定义

| 指标 | 含义 | 方向 |
|---|---|---|
| 拒答召回 `insufficientEvidenceRecall` | 8 条不可答问题里，系统正确拒答的比例 | 越高越好 |
| 编造率 `fabricationRate` | 8 条不可答问题里，仍给出具体事实结论的比例 | 越低越好 |
| 含糊率 `hedgeRate` | 未明确拒答但通篇不确定表述的比例 | 越低越好 |
| 误拒率 `falseRefusalRate` | 14 条可答问题里被错误拒答的比例 | 越低越好 |
| 忠实度 `faithfulness` | 可答回答与标注事实一致、且未添加参考外事实的比例 | 越高越好 |
| hit@1 | 第一条证据是否命中标注事实 | 越高越好 |

拒答/编造的判定由 **LLM 裁判**（同一模型）给出，并保留**纯字面规则**判定作为交叉校验；裁判与规则分歧过大时在 `judgeRuleAgreement` 中暴露，提示该重跑而不是照抄数字。

> **C 组的「是否拒答」用系统自身的 `unanswerable` 决策，不交给裁判代答**——那正是要被度量的东西，交给裁判等于自己给自己打分。忠实度则三组统一送裁判，保证可比。

### 1.4 复现方式

```bash
npm run eval:ablation              # 全量三组（约 124 次模型调用）
npm run eval:ablation -- --limit 4 # 冒烟：每组前 4 条
npm run eval:ablation -- --no-judge # 跳过裁判，指标退化为规则判定
npm run eval:retrieval             # 只跑检索层（零模型调用，可离线复现）
```

| 组 | 拒答召回 | 编造率 | 含糊率 | 误拒率 | 忠实度 | hit@1 | 模型调用 | 平均延迟 |
|---|---|---|---|---|---|---|---|---|
| A 裸 LLM | 0.625 | **0.250** | 0.125 | 0.000 | 0.286 | — | 22 | 1120 ms |
| D 朴素 RAG | 1.000 | 0.000 | 0.000 | 0.000 | 0.714 | 0.917 | 22 | 1076 ms |
| **C 本系统** | **1.000** | **0.000** | **0.000** | **0.000** | **0.929** | **0.929** | **14** | **631 ms** |

补充：检索层单独评测（零模型调用，`npm run eval:retrieval`）

| 组 | hit@1 | hit@3 | MRR | 拒答召回 | 误拒率 |
|---|---|---|---|---|---|
| B 纯 BM25 top 3（无闸门） | 0.714 | 1.000 | 0.845 | **0.000** | 0.000 |
| C 检索层（BM25 + 审校过的 subject/intent 约束） | 0.929 | 0.929 | 0.929 | **1.000** | 0.000 |

**B 组那一列 0.000 值得单独看一眼**：纯词法检索对 8 条不可答问题**一条都没拒**（0/8），全部给出了看似相关的资料。词法分数高 ≠ 资料能回答问题——这正是「高分不能授权作答」这句设计原则的实测依据。

## 三、关键证据：A 组的 3 条失效个案

这是整份报告里最有力的部分。以下是模型**原文**，不是转述。

### 3.1 编造食品安全参数 —— q031「瓜豆酱发酵的安全温度」

> 瓜豆酱（河南乡土西瓜豆酱）发酵的安全温度通常控制在**25～30℃**之间，最佳为**28℃**左右。温度**低于20℃**时发酵缓慢、易杂菌污染；**高于35℃**时易过酸、发臭或产生有害物质。发酵期间应避免阳光直射，保持通风，并注意容器消毒和**盐度控制（一般盐度10%～15%）**，以抑制杂菌、保证安全。

**资料库里没有任何一条发酵温度或盐度的记录。** 上面每一个数字都是编的。

这一条的危险性在于它的**形态**：数字具体、区间合理、术语正确（杂菌污染、盐度控制），读起来像一份技术规范。用户如果照着做，是在用编造的参数处理入口的发酵食品。**这是幻觉里后果最重的一类。**

### 3.2 先免责再编造 —— q030「磨棒每小时能加工多少斤」

> ……因此**没有**「每小时加工多少斤」的固定产量数据。若指传统石磨（常配磨棒/磨棍使用），其加工效率取决于磨盘大小、人力或畜力、粮食种类和操作熟练度，**一般每小时可磨面粉或糁类约20—50斤**；若指现代小型磨粉机，则**每小时可达100—300斤以上**。

前半句说「没有数据」，后半句照样给出两段具体产量区间。**「先免责、后编造」是最阴险的模式**——用户读到开头的「没有固定数据」会以为模型很诚实，于是更容易相信后面的数字。

顺带一提，模型在这里还把「磨棒」理解成「石磨上用于推转或研磨的棒」——**方向性错误**。资料库里写得很清楚：裴李岗磨盘磨棒是**来回滚碾**，与后世**旋转式**石磨不同。

### 3.3 跑题式幻觉 —— q032「四膜一布古法的开园传说」

模型承认「四膜一布古法并非河南乡土文化中广为人知的固定说法」，然后**把话题转移到信阳毛尖的「开园采茶」民俗**，并编出：

> 传说中，**茶祖神农氏或当地茶仙会在开园日降临茶园**，护佑采茶顺利。

「四膜一布」是资料库里明确标记为**无法证实**的具体技艺故事。模型没有编它，而是编了一个**相邻话题**——用户如果不细看，会以为得到了答案。

## 四、D 组的失败模式：资料明明在，模型却说没有

D 组在不可答问题上表现完美（拒答召回 1.000、编造率 0.000）。**这一点必须如实承认**——给全资料 + 明确提示，强模型确实也能拒答。

但 D 组在**可答问题**上塌了：14 条里 4 条被判 `contradicted`，其中 **3 条是「资料里明明有，模型却说资料不足」**：

| 问题 | 参考事实 | D 组的回答 | 裁判判定 |
|---|---|---|---|
| q017 大河村经历哪些时代 | 明确列出仰韶、龙山、二里头、商代 | 称资料不足 | contradicted |
| q019 猕猴桃的果心颜色 | 明确提及红心、黄心、绿心 | 称无相关内容 | contradicted |
| q024 郑州第六批非遗名录有多少项 | 明确记载公布 61 项 | 称资料不足、无总项数记录 | contradicted |
| q020 草莓的保鲜库资料 | — | 添加了参考外的种植历史与获奖信息 | contradicted |

**这是朴素 RAG 的典型失败模式，而且比编造更隐蔽**：它表现得「诚实」（说资料不足），用户不会警觉，但实际上是**漏答**——体验上等同于拒答。忠实度 0.714 vs 本系统 0.929，差的就是这 3 条。

结论：**「把资料全塞进上下文」不等于「能找到资料」。** 31 条事实堆在一起时，模型反而定位不到具体那条。检索与闸门层解决的不只是幻觉，还有**注意力稀释**。

## 五、三个可写进技术报告的论点

**论点一：闸门层把编造率从 25% 压到 0。**
8 条资料库无法回答的问题，裸 LLM 有 2 条给出具体事实结论（含食品发酵安全参数）。本系统编造率 0.000，且这 8 条**全部在本地被拦下，模型根本没被调用**。

**论点二：分层检索把忠实度从 0.714 提到 0.929——朴素 RAG 做不到。**
给全资料的 D 组反而有 3 条「资料在手却说没有」。检索层的作用不只是「防编造」，更是「防漏答」。

**论点三：本地闸门省 36% 模型调用、降 41% 延迟。**
22 条问题里 8 条（全部不可答）在本地零调用解决 → 模型调用 22 → 14 次，平均延迟 1076 → 631 ms。**这是可直接换算成成本的工程收益**，也是「闸门不是负担、是节省」的实测依据。

## 六、已知短板与局限（必须诚实报告）

技术报告里主动写出局限，比被评委问出来强。

### 6.1 本系统的唯一失分：q024

C 组 14 条可答问题里 13 条 `consistent`，唯一失分是 q024「郑州第六批非遗名录有多少项」，裁判判 `irrelevant`（「未回答项数，仅提及西瓜栽培技艺」）。

这条同时是**本地闸门和模型的共同弱项**：闸门把它归到 `watermelon` + `batch`，候选里给了 `f-heritage-batch`（含「61 项」），但模型没有把数字取出来。**已知待修**。

### 6.2 裁判是同一个模型

拒答与忠实度的判定由 `deepseek-flash` 自己给出，存在**自我偏好**风险（倾向于认为同族模型的输出合理）。本报告用**纯字面规则**做了交叉校验，裁判与规则的拒答判定一致率在 0.50–0.875 之间——**A/D 组的一致率偏低（0.50 / 0.625）说明裁判本身有噪声**。

**因此本报告只把数字用于组间对照，不作为绝对评价。** 建议后续引入人工抽检或第二个厂商的模型做裁判。

### 6.3 样本量小

22 条，比率的分母只有 8 和 14。**单条翻转即带来 0.125 的跳变**（例如拒答召回 0.625 → 0.750）。数字应当读作趋势，不是精确值。

### 6.4 A/D 组与 C 组的输入不完全对称

C 组额外获得页面上下文 `placeId`（用户在某个页面提问时系统本来就有这个信息），A/D 组只给问题文本。这是**系统真实输入**与「裸问」的差异，方向上对 C 组有利。影响有限（`placeId` 只在候选排序中作为 0.5 的加权加成），但应当披露。

### 6.5 标注待独立复核

评测集的 32 条标注由工程人员按公开事实 ID 编写，`labelStatus` 中已声明**待队友独立复核**。`relevantFactIds` 若标错，hit@1 与忠实度都会受影响。

### 6.6 实验过程中发现并修复的数据缺陷

跑第一轮时 C 组误拒率异常偏高（0.143）。追查发现**不是模型问题，是评测数据引用错误**：

- q004 / q019 / q026 的 `placeId` 写成 `autumn-field`，而 catalog 里根本没有这个地点（正确的是 `autumn-orchard`，「辰耕基地的猕猴桃故事」）
- 系统于是返回「**没有找到这个文化条目，请重新选择**」——一条给用户的报错文案，被当成模型拒答计入了指标
- 修正后：误拒率 0.143 → **0.000**，检索层 hit@1 0.857 → **0.929**

数据集版本已升为 `culture-seed-2026-09-28-v2`，并在 `scripts/check-project.js` 新增静态检查：**评测集里的 `placeId` / `relevantFactIds` 必须真实存在于 catalog**，否则 `npm run check` 直接报错。

> 这条教训值得单独记：**评测数据引用错位会静默污染实验结论**，而且它伪装成模型失败。修完之后模型指标"变好了"——这正是为什么必须先证明"是数据错了"再改，而不是反过来调模型。
