# 检索层因子实验：我们的检索质量有多少来自算法，多少来自人工标注？

**日期**：2026-09-28
**评测集**：`evaluation/culture-seed.json` · `culture-seed-2026-09-28-v2` · evaluation 拆分 22 条（14 可答 + 8 不可答）
**向量模型**：`qwen3-vl-embedding`（DashScope 原生多模态端点，2560 维）
**脚本**：`scripts/evaluate-retrieval.js --dense`（`npm run eval:retrieval -- --dense`）
**原始数据**：`test-results/retrieval-evaluation.json`

---

## 一句话结论

**检索质量主要来自语义模型，不依赖人工标注**——纯稠密检索（零人工标注）hit@1 达到 0.929，与带标注的 BM25 闸门持平，MRR 0.964 还是全场最高。

同时得到一个反直觉的负结果：**等权 RRF 融合反而变差**（0.786 < 0.929）。

---

## 一、为什么做这个实验

当前检索层的 hit@1 是 0.929，但这个数字是靠 `evidence.js` 里**人工审校过的 subject/intent 标注**（13 个 subject 正则 × 22 个 intent 正则 × 31 条事实的映射）撑起来的。

评审完全可能追问一句：

> **「你们这个 0.929，有多少是算法，有多少是人工标注？」**

如果答不上来，检索层的技术含量就会被判定为「人工规则」。所以设计一个 2×3 因子实验，把这两个来源拆开度量。

## 二、实验设计

| 因子 | 水平 |
|---|---|
| **排序器** | 词法 BM25 / 语义稠密 / 混合（RRF 融合） |
| **人工审校标注** | 用（subject+intent 闸门）/ 不用 |

六组：

| 组 | 排序器 | 用标注 | 说明 |
|---|---|---|---|
| 1 | 词法 | 否 | 纯算法基线 |
| 2 | 稠密 | 否 | 纯算法基线 |
| 3 | 混合 | 否 | 纯算法基线 |
| 4 | 词法 | 是 | 当前线上行为 |
| 5 | 稠密 | 是 | — |
| 6 | 混合 | 是 | — |

**索引文本只取资料本身的标题与正文，绝不掺入 annotations 里的审校关键词**——掺进去就等于把人工标注偷偷搬进向量层，对照实验立刻失去意义。这是本实验成立的前提。

## 三、结果

| 组 | hit@1 | hit@3 | MRR | 拒答召回 | 误拒率 |
|---|---|---|---|---|---|
| 1 纯 BM25 top3（无标注） | 0.714 | 1.000 | 0.845 | 0.000 | 0.000 |
| **2 纯稠密 top3（无标注）** | **0.929** | 1.000 | **0.964** | 0.000 | 0.000 |
| 3 BM25+稠密 RRF top3（无标注） | 0.786 | 1.000 | 0.893 | 0.000 | 0.000 |
| 4 BM25 + 审校标注闸门 | 0.929 | 0.929 | 0.929 | **1.000** | 0.000 |
| 5 稠密 + 审校标注闸门 | 0.929 | 0.929 | 0.929 | **1.000** | 0.000 |
| 6 BM25+稠密 RRF + 审校标注闸门 | 0.929 | 0.929 | 0.929 | **1.000** | 0.000 |

## 四、三条发现

### 发现一：语义模型可以替代人工标注做召回

**纯稠密（零人工标注）hit@1 = 0.929，与带标注的 BM25 闸门完全相同；MRR 0.964 反而是全场最高。**

这意味着：现在那套 13×22 的 subject/intent 标注，**在「找到正确事实」这件事上并非不可替代**。语义模型不用任何标注就能达到同样水平。

### 发现二：等权 RRF 融合是负收益（反直觉）

**0.786 < 0.929。** 融合反而比最好的单路更差。

原因：RRF 隐含假设「参与融合的排序器质量相当」。这里不成立——BM25 hit@1 只有 0.714，稠密有 0.929。等权融合等于让弱排序器给强排序器的正确结果投反对票，把整体拉下来。

**这提示一个通用工程原则：融合之前要先度量各排序器的单独质量，质量不对等时应加权或干脆不用融合。**

> 我们尝试过加权（在 dev 拆分上扫了 0.05–1 共 9 个权重）。但 **dev 拆分只有 7 条可答问题，单条翻转就是 0.143 的跳变**，扫出来的「最优权重」是噪声。因此**没有采用任何调参后的权重**，上面报告的是未调参的等权结果。详见第六节。

### 发现三：闸门之后的候选池恒为 1 条 —— 排序层在闸门之后是冗余的

这一条解释了为什么第 4/5/6 组**数字完全相同**。

实测统计（全部 32 条评测问题）：

```
候选池大小分布：{ 0 条: 11 个, 1 条: 21 个 }
平均候选池 = 1.00   ← 通过闸门的用例，候选永远只剩 1 条
池 > 1 的用例：无
```

**闸门用 `subject` + `intent` 两个离散标签，直接定位到唯一一条事实。** 一旦过了闸门，候选就只有一条，**无论用什么排序器结果都一样**。

也就是说，当前架构实际上是**「闸门即检索」**：BM25 只在闸门之前的 31 条上打分，而打分结果经过 `supported` 过滤后就只剩一条——排序器没有发挥空间。

**这条已固化成测试**（`tests/retrieval-fusion.test.js` 的 `the gate compresses the candidate pool to a single fact`）。一旦标注被改宽、池不再恒为 1，测试会提醒我们排序层开始有意义了。

## 五、架构结论与两条路线

### 现状（路线 A）：闸门即检索

```
L2 闸门（subject+intent 离散标签） → 唯一候选 → 模型只能选它
```

- **优点**：拒答召回 1.000、候选唯一、完全可控、可审计
- **缺点**：**强依赖人工标注**。加新语料、加新问法都要重新标注；标注没覆盖到的问法会直接落进拒答

### 备选（路线 B）：稠密召回 + 闸门只做「能否答」

```
L3 稠密召回 top-K（零标注） → L2 闸门只判定能否回答 → 模型从 K 条里选
```

- **依据**：稠密 hit@1 0.929 已与闸门持平，且**完全不需要标注**
- **好处**：扩展语料不用重新标注；对未见过的新问法泛化更好
- **代价**：候选从 1 条变成 K 条，模型选错的空间变大；需要重新验证忠实度

> **本轮不做切换。** 理由：切换会改变整个管线的行为，必须重新跑完整消融（含忠实度与编造率）才能下结论。当前先把两条路线的依据备齐，供技术报告使用。

## 六、局限与自查

**1. 权重未调参，等权结果不代表最优。** dev 拆分只有 7 条可答问题，单条翻转即 0.143 跳变，不足以支撑任何权重选择。我们**没有**在 evaluation 拆分上调参——数据集明确写着「evaluation 冻结用于报告，不据测试结果调优门限」。

**2. 样本量小。** 22 条，hit@1 的分母是 14。单条翻转 = 0.071。

**3. 稠密的检索质量受向量模型本身限制。** 换模型可能得到不同结论；本实验只测了 `qwen3-vl-embedding`。

**4. 「无标注」三组在拒答上必然是 0。** 它们没有闸门，不会拒答——这不是缺陷，是设计。它说明：**拒答能力完全来自闸门，排序器不提供任何拒答能力**。这一点值得单独强调。

**5. 标注待队友独立复核**（`labelStatus` 已声明）。`relevantFactIds` 若标错，hit@1 会直接受影响。

### 踩到的坑（文档没写，实测才知道）

**`qwen3-vl-embedding` 单次请求的 contents 不得超过 20 条。** 31 条事实一次提交直接报 `InvalidParameter: batch size is invalid, it should not be larger than 20`。已在 `embedding.js` 里按 20 条分批。

**端点选型**：`qwen3-vl-embedding` 走 **DashScope 原生多模态端点**（`/api/v1/services/embeddings/multimodal-embedding/multimodal-embedding`），**不在 OpenAI 兼容端点上**（兼容端点返回 404）。选多模态向量而非纯文本向量的理由：文本与图片在同一语义空间，**L8 跨模态检索可以直接复用同一个索引**。

### 一笔待决的账

`miniprogram/lib/evidence.js` 新增的融合代码让**主包从 2,040,136 → 2,043,026 字节（+2.9 KB）**，余量降到约 54 KB。

问题在于：**小程序端拿不到向量，这段代码在小程序里是死代码**。保留它的理由是「单一实现、不会出现两份排序逻辑漂移」；代价是占掉 5% 的剩余配额。若后续主包吃紧，可以把它移到服务端模块，用 `evidence.answerFromEvidence()` 重新计算答案——但那会引入选择逻辑的重复。**先记账，等主包接近上限时再处理。**
