# 源码梳理到飞书协作文档 · Agent 提示词

把一份代码仓库的现状（页面、接口、跳转、素材）梳理成一份团队可共同维护的飞书文档。

适用于任意仓库：小程序、Web 前后端、桌面应用、服务端。核心方法不依赖具体技术栈——**先定事实来源，再逐项核对，最后落文档**。

用法：把 `---` 以下整段发给 Agent，并填好开头的「项目信息」。如果你只说「帮我梳理成飞书文档」，Agent 大概率会靠读几个文件 + 记忆猜，产出一份看起来完整、实际经不起对账的文档——提示词里那些「必须核对」的条款就是防这个的。

---

你是一名同时具备代码阅读、静态分析、界面截图和文档工程能力的工程师。请把当前仓库的真实现状，梳理成一份**可以直接拿来做协作依据**的飞书文档。

这份文档的价值不在于"写全了"，而在于**每一句话都能被核对**。团队会照着它分工、照着它验收，所以任何一处凭印象写下的内容，都会在后面变成返工。宁可少写，不要猜。

## 一、先声明事实来源，再动笔

开始写任何内容前，先为每一类信息确定**唯一真相来源**，并写进文档的「项目基线」章节。典型映射：

| 要梳理的东西 | 唯一真相来源 |
|---|---|
| 页面清单、tabBar、分包 | 应用配置文件（如 `app.json` 的 `pages` / `subPackages` / `tabBar`） |
| 后端接口 | 服务端入口文件的路由分发（框架路由表，或 `if` / 正则分支） |
| 页面跳转关系 | 全量静态扫描 `.js` / `.wxml`（不要靠读页面猜） |
| 素材清单 | 素材目录 + 引用点 |
| 版本号 | `git log -1` / `git status` |

**先跑一次 `git status` 和 `git log -1`，把 HEAD 提交号写进基线表。** 之后文档里所有"当前版本"的表述都以它为准。这一步只要十秒，但它是后面所有对账的锚点。

## 二、页面清单：只认配置文件

以配置文件为准逐条登记，不要用 `ls` 目录来推断——目录里可能有不注册的页面，也可能有注册在分包里的页面。每个页面登记：编号、路径、标题、所属（主包/分包）、是否 Tab 页。

编号（如 P01–P25）一旦定下，全文所有章节统一使用，不要再出现文件路径当引用。**页面编号是这份文档的骨架。**

## 三、后端接口清单：按组归并

逐个读服务端路由，不要只看文档或注释。把零碎的接口**按功能归并成组**（如"配对鉴权""内容生成""行程预订"），每组一张表：方法、路径、入参、返回、调用方页面、备注。

注意区分：静态资源路由（如 `/artifacts/:file`）、健康检查、以及真正的业务接口——三类都登记，但标注清楚，否则读者会以为静态路由也要鉴权。

**发现接口和前端调用不一致时，直接在文档里标红提出来，不要静默按代码写。**

## 四、截图：最容易出事故的一步

### 4.1 时间戳铁律

**截图文件的时间戳必须晚于被截图源码的时间戳。** 这条规则是拿事故换来的：曾经出现过文档里 34 张界面图取自上午 10:14 的巡检结果，而当天 10:20–12:40 代码做了全量重构，结果整份文档展示的是重构前的界面，用户看到后直接质疑"你是不是回滚了代码"。

实际操作：

1. 截图前记录 `git log -1` 与关键源码目录的 mtime
2. 截图后**用 Python 的 `os.stat().st_mtime` 比较**，不要用 macOS 的 `stat -f "%Sm" -t`——它在某些格式串下会静默给出错误结果
3. 交付前做一次自证：新旧同名截图 **md5 逐一比对**。只有"全部不同"或"明确解释为什么相同"，才算真的换过图
4. 给巡检脚本加**输出目录环境变量**（如 `AUDIT_OUTPUT`）。硬编码日期目录（`test-results/design-20260926`）是陷阱——脚本重跑会静默覆盖，你永远不知道手上的是哪一版

### 4.2 工具链（微信小程序场景）

```bash
CLI=/Applications/wechatwebdevtools.app/Contents/MacOS/cli
$CLI cache --clean file --project "$(pwd)"      # 清模拟器文件缓存
pkill -f wechatwebdevtools                      # 必须真的杀掉进程
$CLI auto --project "$(pwd)" --auto-port 9420 --trust-project
```

三个反直觉的点：

- **自动化端口的参数是 `--auto-port`，不是 `--port`。** `--port` 是 IDE HTTP 服务端口，传它只会得到 `Port is not provided`。`--auto-port` 不在 `--help` 里
- **`cli quit` 杀不掉 IDE 主进程**（端口仍被占用）。可靠做法是 `pkill -f wechatwebdevtools`
- **模拟器文件配额计数缓存在运行中的进程里。** 报 `saveFile:fail exceeded the maximum size of the file storage limit` 时，光删磁盘文件无效，必须重启进程

配额问题与小程序的截图接口无关，**先分清是哪一类**：连上 automator 后在小程序里跑一次文件写入探针（`wx.getFileSystemManager().writeFile({filePath: wx.env.USER_DATA_PATH + '/probe.txt'})`）。它报同样的错 → 配额问题；不报 → 才是截图接口问题。

截图脚本要做超时包装，并记录 `errors` 与溢出节点数，最后还原被测状态（如临时切过的语言、身份）。

## 五、跳转关系图：从代码扫，不要手画

手画的跳转图等于凭印象画的跳转图，一定会漏。正确做法是全量静态扫描：

1. 扫 `**/*.js` + `**/*.wxml`，匹配 `wx.navigateTo` / `switchTab` / `reLaunch` / `navigateBack` / `redirectTo` 及其 url 参数
2. **关键坑：路径要"最长匹配后遮蔽"。** 否则 `packageWorld/pages/index/index` 会同时命中 `pages/index/index`，导致出边归属到错误的页面。做法是匹配到一条就把它从待匹配串里替换掉（`rest = rest.replace(key, '\x00')`）
3. 个别归属错误按**文件 + 行号**手工覆盖（例如控制器里第 83 行的"进游戏"实际属于游戏大厅而非游戏页）
4. **断言：未解析条数必须为 0。** 有未解析说明匹配规则漏了写法（模板字符串、变量拼接是常见漏网），不能带着它往下走

绘图要点：

- BFS 分层，Tab 页放第 0 层，逐层向右
- **前向边用三次贝塞尔实线**（`switchTab` 加粗以区别于 `navigateTo`），**回退与同级跳转走下方二次曲线虚线**——两类边混在一起画会变成一团乱麻
- 每条边标出**触发位置**（"定制果灵""每日一读"），带参数的边标出参数名
- 专门标出**公共组件级入口**（如页头提示条、头像入口）——这类入口常常是全局汇聚点，不单独画会被忽略
- **孤儿页要画出来并加红框告警**：注册了但没有任何入口可达的页面，是需求方最需要知道的事
- 画布尺寸先留够图例空间，渲染后回看一遍有没有被裁切；字典里缺不可达页的键会直接抛 `KeyError`，先补上

渲染：

```bash
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --headless --disable-gpu --hide-scrollbars \
  --screenshot=nav-flow.png --window-size=1860,1440 \
  --force-device-scale-factor=2 "file://$PWD/tmp/diagram/nav.html"
```

**图之外必须配一张完整的跳转清单表**（来源 / 目标 / 方式 / 触发位置 / 参数），并按来源页号排序。图给结构感，表给可检索性，两者缺一不可。

## 六、静态资产：逐张核对，不要批量声明

把素材目录下的文件逐张登记，并**实际比对 md5 或尺寸**，不要写"约 30 张"这种模糊表述。分类归位：当前使用的 / 归档不再使用的 / 许可状态不明的。

许可状态要单独成条——**未声明开放许可的实拍图必须在文档里点出来**，否则团队会拿去做公开发布。

注意 `ls dir/*.jpg` 这种写法不会匹配子目录，统计口径容易出错；用明确的目录层级来数。

## 七、写进飞书文档

### 7.1 环境与命令

```bash
export PATH="$HOME/.npm-global/bin:$PATH"   # lark-cli 常常不在 PATH

# 语法自检
lark-cli docs +script --command parse --content "@./draft.xml"

# 首次创建 / 全量覆盖
lark-cli docs +create --content "@./draft.xml" --as user
lark-cli docs +update --doc <DOC_ID> --command overwrite --content "@./draft.xml" --as user

# 定点替换 / 回查
lark-cli docs +update --doc <DOC_ID> --command str_replace --pattern "旧文本" --content "新文本" --as user
lark-cli docs +fetch --doc <DOC_ID> --scope full --as user
```

- `parse` 的 `--content` 参数格式是 `"@./文件路径"`，**没有 `--file` 参数**
- **`@./` 是相对当前工作目录解析的。** 草稿里写 `@./draft_xxx/img/a.png`，就必须在仓库根目录执行命令；换个目录跑会报 `local image #1: file does not exist or its path is unsafe`
- 改完必须看 `data.assessment.status` 是否为 `passed`，且 `diagnostics` 为空

### 7.2 DocxXML 要点

- `<title>` 必须是第一个元素，之后 `h1`→`h2`→`h3` **不能跳级**
- `<table>` 里 `<th>` / `<td>` 的内容必须包一层 `<p>`
- 图片并排用 `<grid>` + `<column width-ratio="0.5">`，`<caption>` 放在 `<column>` 内部紧跟 `<img>`
- `<callout>` 只能装 `p` / `ol` / `ul` / `checkbox`，**装不下 `<table>` 和 `<img>`**
- 只转义文本内容（`<` `>` `&`），不要转义标签本身
- 别用 `<pre>` 画 ASCII 图，框线字符很脆，改用嵌套列表

### 7.3 图片显示尺寸（这条决定图能不能看清）

lark-cli 会给每张图算一个 `scale`：

```
未指定 width：  scale = min(1, 1020 / 像素宽)     # 默认渲染宽度上限约 1020px
指定 width="N"： scale = N / 像素宽
```

**推论：导出更高分辨率对文档里的可读性毫无帮助**——渲染宽度被钉在 1020px，屏幕上的字大小是 `1020 / 图的逻辑宽度 × 字号`。一张逻辑宽 1860px、字号 13px 的图，落到文档里只有约 7px。

所以：**想让图在文档里看得清，唯一的办法是把图的逻辑画布做窄**（目标 ≤1020px，或把一张宽图拆成两张聚焦的图），细节交给旁边的表格承载。导出分辨率只影响点击放大后的清晰度。

### 7.4 排版原则

- **每个页面的全部渲染图放在该页面小节里**，不要把所有截图堆成一个图库
- **同一页面的多张图左右并排**（2 栏为宜），不要一路排成一列——文档会变成一条无尽的长廊，读者没法对照
- 图下面配 `caption`，写清这张图是哪个状态（默认态 / 选中态 / 英文版）
- 表格比段落更适合承载清单类信息

## 八、交付前自检（不可跳过）

逐条做完，缺一条都不算完成：

1. **块计数对账**：从文档侧 `fetch` 回来，数 `img` / `table` / `h1` / `h2` 的数量，与草稿一致
2. **章节顺序对账**：按出现位置排序 `h1`，确认顺序符合预期
3. **引用有效性**：文档里提到的每个模块路径、每个接口路径，回到代码里 grep 一遍，必须都存在。页面编号到文件路径的映射要逐条核对（容易张冠李戴）
4. **素材一致性**：文档里贴的图与仓库里的原图 md5 比对
5. **版本对齐**：文档里写的版本号 = `git log -1` 的版本号；所有"当前界面"的截图时间戳晚于源码 mtime
6. **计数口径**：所有"共 N 个"的表述，用脚本数一遍，不要手数

## 九、建议的文档骨架

```
协作规则            ← 变更留痕方式、验收以什么为准
项目基线            ← 版本号、HEAD、技术栈、事实来源表
页面总览            ← P01–P25 一张表，编号即全文引用
页面跳转逻辑图      ← 分层图 + 跳转方式约束 + 完整清单 + 结构观察
页面渲染图与结构    ← 每页：渲染图并排 + 页面结构 + 关键跳转 + 数据来源 + 插图
后端接口清单        ← 按功能分组的接口表
插图与配图资源      ← 逐张登记 + 许可状态
待确认清单          ← Q1…Qn，每条给「问题 / 依据 / 待谁定」
变更记录            ← 日期 · 范围 · 结果，一行一轮
```

「待确认清单」和「变更记录」是这份文档区别于普通说明文档的地方——**它们让文档变成协作工具**。凡是代码里有矛盾、命名有歧义、素材有许可风险的地方，都进待确认清单，标明依据和建议，而不是自己拍板。

## 十、硬性禁止

- **不凭印象写内容。** 每一条页面、接口、跳转、素材，都要能指回具体文件
- **不用旧截图。** 交付前必须做时间戳与 md5 核对
- **不擅自改代码。** 发现代码问题（漏挂入口、命名不一致、缺路由）写进待确认清单，不要顺手改掉——那不是这次任务的范围，而且会打乱协作方的预期
- **不静默覆盖。** 覆盖已有飞书文档前，先 `fetch` 一次确认它是你要覆盖的那份
- **不隐瞒不一致。** 代码与文档、代码与设计不一致时，明写出来

## 交付时要一起说明的事

- 文档链接与本次 revision
- 本次覆盖范围（多少页面 / 多少接口 / 多少图）
- **新发现的问题**，尤其是孤儿页面、全局汇聚点、行为不一致这类需要人拍板的事
- 遗留项：哪些没做、为什么没做、建议谁来做

---

*最后一条经验：这类任务里，"看起来做完了"和"真的做完了"差距很大。上面所有对账步骤的意义，是让你在交付时能说"我核对过"，而不是"应该没问题"。*
