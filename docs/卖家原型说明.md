# 农产品卖家本机原型

入口为“我的 → 我是农产品卖家”，页面路由 `pages/seller/index`。2026-09-22 起页面底部固定两个分区：**左「AI预测」、右「我的」**。「我的」承载种植情况填报与记账（子标签：我的批次、经营更新、执行记录）；「AI预测」承载天气 + 游客人流量信号、库存测算、AI 滞销解读与文旅方案（子标签：风险测算、方案工坊）。所有经营操作只写本机账户分区，不入驻商户、不发布活动、不收款。

## AI预测的三个信号与边界

- **天气**：`miniprogram/lib/weather.js` 按批次地区（地级市）坐标请求 Open-Meteo 公开气象（免密钥、非商用条款），取未来 7 天降雨/气温，并标注接待/采收窗口内的降雨天数；失败或无城市映射时如实显示“未知”，不编造天气。
- **游客人流量**：`miniprogram/lib/visitor-flow.js` 在游客侧行程生成成功时（行程页 build）按“地点 + 出行月份”做本机匿名计数（行程次数与人数，无任何个人信息，最多保留 6 个月）。例如九月份游客定制含“河南博物院”的行程，会计入九月该地点人次；果农「AI预测」按所在市读取该信号。这是**本机设备范围**的聚合，不是全网游客统计。
- **AI 解读与方案**：`POST /api/seller-insight`（DeepSeek）输入批次摘要、规则测算数字、天气与游客信号，输出滞销解读、建议与受约束的文旅方案步骤。**风险状态只能由库存平衡规则给出，模型必须原样回显 status，回显不一致即整体作废回退**；建议 2–4 条、步骤 3–6 步、容量/预算不得超出规则上限；模型关闭或失败时回退本机规则解读。AI 生成的方案以 `ai-insight` 模式单独存档，明确标注“AI 草案，数字与状态以本机规则测算为准”。

## 数据与真实性

- 个人账户首次进入是空白；演示账户使用 `seller-sample.js` 生成相对当日的模拟经营批次。批次、方案和反馈显式标注模拟，禁止拿来证明预测精度或实际助农效果。
- 模拟批次的地区为河南中牟，数量、时间、品种、人员与接待条件均为虚构演示参数，不声称存在该农户或该季节的真实经营活动。
- 文化依据引用既有 catalog 的事实和原始来源。中牟西瓜草案引用瓜豆酱资料；其他河南批次可以延伸阅读裴李岗农具，但明确不把馆藏归属到卖家产地；未收录的全国地区不自动虚构文化事实。
- 全国省、市、县通过微信地区选择器填写，作物允许自填。面积保存为亩，重量保存为公斤，支持公顷、斤、吨输入。
- 顶层 `seller` 字段独立于出游画像，使用 `capturePartition/readPartitionField/writePartitionField`。页面切换账户会清空未保存表单并重新加载；仓储调用显式绑定发起账户。

## 库存口径

期初库存定义为建账时已经采收、仍可销售的数量。预计总产量范围包含此数量及以后采收入库。已在建账前卖出的产品不纳入本批台账。

| 记录类型 | 库存变化 | 待交付变化 |
| --- | --- | --- |
| 采收入库 | 增加 | 不变 |
| 现货销售（已交付） | 减少 | 不变 |
| 确认订单（未交付） | 不变 | 增加 |
| 订单交付 | 减少 | 减少，必须关联订单 |
| 取消未交付订单 | 不变 | 减少，必须关联订单 |
| 可重新销售的退货 | 增加 | 不变，必须关联已交付销售 |
| 损耗 | 减少 | 不变 |
| 当天销售已核对 | 不变 | 不变，明确包括零销量 |

库存守恒为 `期初库存 + 采收入库 − 已交付销售 + 退货 − 损耗`。不允许负库存、超额交付、超额取消或超额退货。同一事件编号重复提交只写一次，不同内容复用编号会报错。已有经营记录时不可改写期初库存和建账日期。

经营事件最多 5000 条、批次最多 100 个；达到上限保留原记录并提示导出备份。页面提供复制整个经营数据 JSON 的本机备份入口。

## 压力测算

- 以当日开始的未来最多 7 天为窗口，包含当日，并截到可售截止日期。剩余可售天数不超过 3 天且预计有剩余时为“临近截止仍有缺口”。
- `预计剩余量 = 窗口内可售供给 − 确认待交付 − 预计新增净销售`，界面将负剩余显示为零，另提示订单供给不足。
- 最近 7 天内至少有 3 天显式核对的历史净销量时，以这些已核对日的均值估计新增销量；未核对日不擅自补零。
- 记录不足时仅采用卖家明确填写的假设，`0` 是有效零销量假设，留空表示未知。原型不给滞销概率。
- 采收窗口内的预计待采供给为“预计总产量减期初库存及累计采收入库”，按余下采收天数均摊。页面保留产量范围和假设说明。未知产量、期限过期和缺少销量依据显示“信息不足”。
- 天气与旅游信号目前显示未知，不因缺数据自动制造好天气或高需求。超过 7 天未核对销量会提示数据陈旧。
- 提醒按批次、状态和可售截止日期去重，保留已读、处理和复盘；状态变更后旧提醒转为历史。

## 方案与执行

方案始终为未确认草案，只保存本机。接待人数按卖家填写容量与“每名工作人员暂按 8 人”的原型假设取较小值；材料预算暂按每位 8 元，不含人工、保险、交通与场地。均需举办前核实，不能据此承诺安全接待或价格。

接待人员、日期、交通或容量不足时只提供预售和渠道协作流程。文化依据、步骤、预算、待确认项、雨天替代方式一并保留。没有雨天场地就建议暂停到访，不编造室内空间。

执行反馈记录参与意向人数、已发生支出和文字复盘，不自动生成订单、销量、预约或成交。真实销售需去经营台账另记。

## 验证与后续

运行 `node --test tests/seller*.test.js`。用例覆盖单位换算、非法日期、库存守恒、订单交付不重复扣减、退货上限、零销量、缺失数据、过期资料、待采供给、幂等写入、个人与演示隔离、提醒状态、草案约束及原生页面完整流程。模拟测试不能替代 iOS、Android 真机显示和交互检查。

后续真实多商户阶段再引入身份、服务端数据库、审计账本和天气/旅游来源。积累足够连续真实批次数据后，才比较规则基线、历史均值与经过独立验证的训练模型。

## 当前测算限制

- 历史交付净销量只是未来新增净销量的简单代理，不是已经验证的新增需求预测。仍需结合订单节奏人工调整日销量假设。
- 待交付订单目前没有独立交付期限字段，窗口测算按全部待交付量需在窗口内履约处理；分期订单需要后续增加交付计划。
- 预计待采供给只参与情景计算，不会自动写入库存。实际采收必须另记入库；预计待采量同步减少，避免重复计入供给。
- 台账粒度是日期，同一天按登记顺序对账；不支持小时级履约排程。补录过去事项会重算后续库存并拒绝造成负库存或无效关联的记录。
- 演示样例日期在首次建立时固定。隔日继续查看会自然产生过期或陈旧提示，不会偷偷改写历史；需要重新体验时使用既有“重置演示账户”。
- 同一提醒在持续同一状态期间复用并保留处理标记；压力解除后再次出现时创建新的未处理提醒。
