# 辅助果农场景：可训模型清单

2026-09-27 · 基于 `seller-core.js` / `seller-store.js` / `weather.js` / `visitor-flow.js` / `server/tasks.js` 逐文件审查

---

## 0. 结论先行

这条线上**能训的模型有 6 个，但现在只有 2 个能真的开工**。

原因不是技术，是数据：

| 类别 | 模型 | 现在能不能训 |
|---|---|---|
| **可以自己造数据** | 果实成熟度 / 商品等级分级 | ✅ 现在就能 |
| **不需要标注** | 台账异常检测 | ✅ 现在就能 |
| **需要真实经营序列** | 日净销量预测 | ❌ 卡数据 |
| **需要真实使用行为** | 提醒该不该发（干预决策） | ❌ 卡数据 |
| **需要方案执行记录** | 方案 → 参与意向人数 | ❌ 卡数据 |
| **不该做** | 滞销概率预测 | 🚫 已论证过 |

但后 4 个**数据模型已经全部就绪**——`seller-store.js` 里 `batches / events / riskSnapshots / alerts / plans / feedback` 六张表都在，字段也齐。**问题只是还没有真实数据灌进去。**

## 1. 一个被忽略的事实：规则引擎已经「像个模型」了

`assess()` 的返回值里有这一行：

```js
model: 'inventory-balance-v1'
```

它已经具备一个可对照基线的全部特征：

| 特征 | 现状 |
|---|---|
| **版本化** | `model: 'inventory-balance-v1'` |
| **确定性输出** | `status ∈ {insufficient, clear, attention, urgent}` |
| **量化结果** | `remainingKg`、`supplyKg`、`expectedSalesKg`、`dailyKg` |
| **可解释依据** | `basis: '最近 7 天内 3 天已核对净销量均值'` |
| **明确标注假设** | `scenario` 标志 + `notes` 说明哪些是假设 |
| **训练排除标记** | 顶层 `excludeFromTraining: true`（演示数据） |

**这意味着「规则基线 vs 训练模型」的对照框架已经天然存在，只缺一个被对照的模型。**

而且它现在的 `dailyKg` 估计方式非常朴素：

```js
// 有 ≥3 天已核对 → 取均值
dailyKg = 最近 7 天内已核对日的净销量均值
// 否则 → 用卖家手填的假设
dailyKg = batch.assumedDailyKg   // '卖家填写的日净销量假设 · 情景测算'
```

**两个都是弱基线。这就是模型该补的缺口。**

## 2. 可训数据的真实盘点

| 数据表 | 演示现状 | 上限 | 能训什么 |
|---|---:|---:|---|
| `batches` 批次 | **1** | 100 | 批次属性特征 |
| `events` 经营事件 | **7 条 / 4 天** | 5000 | 日净销量序列（**目标变量**） |
| `riskSnapshots` 风险快照 | **0** | 200 | 状态时序特征 |
| `alerts` 提醒 | **0** | 200 | **`read`/`handled`/`review` → 弱标签** |
| `plans` 方案 | **0** | 100 | 方案特征 |
| `feedback` 执行反馈 | **0** | 300 | **`intentCount` + `actualCost` → 效果标签** |
| `visitor-flow` 游客信号 | 本机匿名计数 | 6 个月 | 需求侧特征 |

**可用于训练的样本数：0。**

但数据模型里已经埋好了两个关键钩子：

1. **`excludeFromTraining`** —— 演示/合成数据自动排除，不用人工筛
2. **`feedback` 表把「方案」和「实际结果」连起来了** —— 这是效果建模的监督信号

### 训练目标的原型已经存在

`ledger()` 返回的 `daily` 就是日净销量序列：

```
2026-09-24 → 30 kg
2026-09-25 → 30 kg
2026-09-26 → 30 kg
2026-09-27 →  0 kg
closedDates（卖家显式核对的日子）= 09-24, 09-25, 09-26
```

`closedDates` 尤其重要——它是**卖家主动确认过**的日子，比自动推算的日子可信。这就是监督信号的天然权重。

## 3. 六个可训模型

### ✅ A. 果实成熟度 / 商品等级分级

**为什么放第一：这是「辅助果农」里唯一现在就能训出真东西的。**

| 项 | 内容 |
|---|---|
| **任务** | 果实照片 → 成熟度等级（未熟 / 适熟 / 过熟）或商品等级 |
| **技术含量** | 细粒度视觉分类 + **序数回归**。等级是**有序的**，不能当普通多分类——「把适熟判成未熟」和「把适熟判成过熟」的错误代价不同 |
| **主指标** | **QWK（二次加权 kappa）** —— 序数分类的标准指标，有文献可引，且相邻错误的惩罚小于跨级错误 |
| **对照基线** | ① Qwen-VL zero-shot（现有 `/api/identify-fruit` 的通用能力）② 人工分级 |
| **数据** | **自己拍 + 标注，可控可扩**。200–400 张即可起步，不依赖任何果农 |
| **成本** | 拍照标注 2–3 天 + 训练 1 天 |

**贴题性**：果农最真实的两个痛点是「**什么时候采**」和「**这批能卖几级**」。现在系统只处理数量，完全不处理质量。补上这一块，辅助果农才完整。

**可讲的叙事**：通用 VLM 在 zero-shot 下对**细粒度成熟度**的判断通常不理想（它没受过农业分级训练）。微调一个专门的小模型，在 QWK 上超过通用 VLM，这是**清晰、可量化、有对照**的结论。

---

### ✅ B. 台账异常检测

| 项 | 内容 |
|---|---|
| **任务** | 从 8 类经营事件里找出可疑记录 |
| **可疑类型** | 日期越界、数量离群（某天销量是均值 10 倍）、类型矛盾（同一天既「已核对」又有大量新销售）、重复录入 |
| **方法** | 稳健统计（MAD / IQR）+ Isolation Forest |
| **主指标** | 注入异常的检出率、误报率 |
| **为什么能立刻做** | **无监督，零标注**。而且评测可以**程序化注入异常**来构造——不需要真实数据 |
| **成本** | 1 天 |

**真实价值**：`ledger()` 一旦遇到负库存就直接抛错，说明录错一笔会让整个测算崩掉。异常检测能在录入时就拦住，这是能演示的实用功能。

---

### ⏳ C. 日净销量预测（核心，但卡数据）

| 项 | 内容 |
|---|---|
| **任务** | 未来 1–7 天日净销量，**点估计 + 预测区间** |
| **目标变量** | `ledger().daily[date]` |
| **特征** | lag1–7 销量、星期几、距可售截止天数、天气（温度/降雨，Open-Meteo 免费可取）、物候/节气、批次属性（作物/品种/面积/产量范围）、`visitor-flow` 游客信号 |
| **方法** | 梯度提升（LightGBM/XGBoost）+ **分位数回归**做区间 |
| **基线（两个）** | ① 近 7 天已核对日均值 ② 卖家填写的 `assumedDailyKg` |
| **主指标** | MAE、MAPE、**区间覆盖率** |
| **硬门槛** | **多批次 × 多天连续序列。现在 1 批次 × 4 天，差两个数量级。** |

**为什么区间比点估计重要**：果农要的不是「明天卖 30 公斤」，而是「明天大概卖 20–45 公斤，所以别一次全摘」。**区间覆盖率**（实际值落在区间内的比例）是比 MAE 更能说明价值的指标。

**⚠️ 警告：不要硬上。** 规划文档 7.7 论证过为什么不做滞销预测——那个判断是对的，理由（批发价 ≠ 某地滞销、年鉴产量 ≠ 当前待售量）都站得住。**没有数据就训，只会得到拟合噪声的模型，答辩时一问就穿。**

**短期替代**：用合成数据跑通训练管线（必须标注「合成数据实验」），报告里写「管线就绪 + 启动门槛」，不写「已完成预测」。

### ⏳ D. 提醒该不该发（干预决策）——**最有意思的一个**

这个方向我认为被低估了。

`alerts` 表的字段：

```js
{ id, key, batchId, label, active, read, handled, review, createdAt, lastAssessedAt, remainingKg }
```

**`read` / `handled` / `review` 三个字段就是天然的弱标签。**

| 项 | 内容 |
|---|---|
| **任务** | 给定当前状态，预测「果农会不会处理这条提醒」 |
| **技术定位** | 这实际是 **uplift modeling / 干预响应建模**，有成熟文献 |
| **主指标** | 处理率预测 AUC、**无效提醒率下降**、与实际处理行为的对照 |
| **价值** | 如果某类提醒果农从来不处理，那它就不该发——现在系统对所有 `attention/urgent` 都发提醒，**没有任何「该不该打扰」的判断** |
| **为什么值得做** | **这是唯一「用得越久越准」且完全不依赖外部数据的方向** |

而且它和「AI 解读」是互补的：现在的 `sellerInsight` 是**让模型写解读**；这个方向是**让模型决定什么时候该介入**。

**注意**：需要真实果农用一段时间才有样本。短期只能把埋点做对（`read`/`handled` 的时间戳、忽略次数），报告里写为「已设计待数据」。

---

### ⏳ E. 方案 → 参与意向人数

| 项 | 内容 |
|---|---|
| **任务** | 批次属性 + 方案特征 → 预测参与意向人数 |
| **方案特征** | 是否含文化环节、`capacity`、`budget`、步骤数、是否有雨天备选、`mode`（规则 / AI 草案） |
| **标签** | `feedback.intentCount` |
| **基线** | **`capacity * 8`（每位工作人员 8 人）这个写死的原型假设** |
| **主指标** | MAE、与容量假设的对照 |
| **定位** | 这是规划文档 8.3「阶段 B：个性化体验排序」的具体落地 |

**基线特别清晰**：`createPlan()` 里 `perVisitorAssumption: 8` 是硬编码的。**模型能打败这个 8，就是明确的增益。**

而且这里有个**天然对照实验**：`plans` 表里同时存了 `mode: 'local-constraints'`（规则方案）和 `mode: 'ai-insight'`（AI 方案）。**同一批次下两种方案的实际效果可以直接比。** 这是评分表要的「对照测试」的现成素材。

---

### 🚫 F. 滞销概率预测 —— 不要做

规划文档 7.7 已经论证清楚：

> 需要预测的对象必须先定义：哪个农户、哪批货、哪段时间、什么条件下算滞销。至少应掌握可售库存、未来采收、订单、渠道成交、保鲜周期与本地价格等，且有历史结果做验证。

**这个判断是对的，守住。** 批发市场价格属于特定市场与交易环节，年鉴年度产量不代表当前待售量。**硬做只会得到一个不可信的数字，反而扣分。**

## 4. 推荐主线：把闭环讲成「训练数据生产机」

「辅助果农」这条线最有说服力的**不是预测**，而是**闭环**：

```
  果农填报批次
       ↓
   经营台账（8 类事件）
       ↓
   规则测算 assess()  →  status / remainingKg / basis
       ↓
     提醒 alerts  →  read / handled / review    ← 弱标签
       ↓
     方案 plans   →  mode: 规则 / AI 草案        ← 可对照
       ↓
   执行反馈 feedback → intentCount / actualCost  ← 效果标签
       ↓
    （回到台账）
```

**这个闭环本身就是一台训练数据生产机。** 果农每用一次，就产生一组 `(状态, 决策, 结果)` 三元组。

所以对外应该这么讲：

> 我们不是「训了个模型去预测滞销」，而是**建了一条能持续生产训练数据的经营闭环**，并用它把规则基线逐步替换为有实测增益的模型。

**为什么这个叙事更好**：

1. **诚实**——数据量确实支撑不了「已训成销量预测模型」，硬说会被问穿
2. **更有分量**——「建了一条能持续产出训练数据的管线」比「训了个模型」更难做到
3. **有依据**——`assess()` 里的 `model: 'inventory-balance-v1'` 说明规则引擎已经版本化了，它就是一个可对照的基线
4. **呼应官方要求**——附件 2 附录要「数据资料 + 数据来源说明」，这条闭环的字段定义就是数据卡

**明确不做的**：不在没有数据的情况下训销量预测，不写「预测准确率 X%」，不把合成数据结果当真实能力。

## 6. 一句话总结

**「辅助果农」这条线上，数据模型已经比 AI 能力走得更远了。**

`events` / `alerts` / `feedback` 三张表的设计——尤其是 `feedback` 把方案和执行结果连起来——说明这套系统**本来就是按「可训练」设计的**。

现在缺的不是架构，是**时间和真实使用**。

所以正确的动作是：**用能自己造数据的那个模型（成熟度分级）先把「自训练 + 独立评测 + 指标对照」这条链路跑通**，同时把其余三个的埋点做对、启动门槛登记好。这样报告里既有「已完成的训练成果」，又有「已就绪的数据管线」——比硬凑一个销量预测模型扎实得多。
