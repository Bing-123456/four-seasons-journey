# 古典模型训练方向与数据可行性分析

- **起因**：2026-09-27，你提出「微调 LLM 的话这个肯定是不够的呀；如果是训古典的一些模型，应该往哪个方向发展」
- **本文档已修订**：初版推荐「意图分类器 + 检索重排器 + 引用支持验证器」三个文本模型。你随后提出质疑——「**这个里面好像确实没啥模型可以训练的**」。**核查代码后，你的质疑基本成立。** 本文档据此重写，修正内容见下。

## 零、修正说明：你对在哪里

初版那三个文本方向的共同毛病是——**标签全部来自我们自己**，没有独立监督信号：

| 初版推荐 | 为什么站不住 |
|---|---|
| **意图/主语分类器** | 训练标签是 `evidence.js` 里 **35 条正则**打出来的。用规则生成标签、再训模型去模仿规则 = **知识蒸馏，教师是规则**。答辩问「你的模型比规则强在哪」，答不上来。而且 31 条标注分 13 个类别，**平均每类 2.4 条**。 |
| **检索重排器** | 候选集**总共 31 条事实**。这不是排序问题，是「31 选 1」。hit@3 已经是 **0.857**，天花板 1.0，**增益空间只有 0.143**。而且问法是我们自己造的，跟真实用户分布不一致。 |
| **引用支持验证器** | 负样本是「把事实里的数字/地名换掉」。**换了一个数字，字面比对就能查出来**——模型学到的是「数字不一样就是假的」，这不是语义支持验证，是字符串比对。要有难度就得构造「语义改写但被支持」的正样本，那需要**人工**。 |

**一句话概括**：这三个都是「**把规则包装成模型**」。技术上能跑通，但答辩撑不住，因为**没有一个信号是独立于我们自己产生的**。

**但这不等于「没啥能训」。你漏了一个——而且恰恰是最像样的那个。**

## 一、先确认：LLM 微调确实不够（这部分初版结论不变）

| 项 | LLM 微调（SFT/LoRA） | 我们现有 |
|---|---|---|
| 指令微调数据量 | 通常 **1,000–10,000 条**（(指令, 回答) 对） | **0 条** |
| 我们最接近的东西 | — | 32 条检索标注（是 (query, 事实ID)，不是指令对） |
| 最小可行量 | 约 500 条起步 | 差 **15–300 倍** |
| 算力 | 至少 1×24G 显存 + LoRA，或租卡 | 未知，需确认 |

**更要紧的一点**：就算我们用 415 条内容**让 LLM 生成**几千条 QA 对来微调，那也是「**自己生成、自己训、自己评**」——评测会失真，答辩时一问就穿。这条路**不建议走**。

> **一个例外**：如果一定要碰 LLM，该做的不是**微调**，而是**评测基准**——用我们的 32 条标注（含 8 条拒答负样本）做一个「**文化领域幻觉评测集**」。这是**数据贡献**，比微调一个模型稀缺得多，而且可以公开。

## 二、关键认知：内容库 ≠ 任务数据集（这部分不变）

**415 条内容不是「不够」，而是「形态不对」。**

| | 内容库（我们有什么） | 任务数据集（模型要什么） |
|---|---|---|
| 形态 | `{id, title, text, sourceIds, season, topic, tags}` | `(输入, 标签)` 或 `(query, doc, 相关性)` |
| 能直接训模型吗 | ❌ 不能 | — |
| **能转换吗** | ✅ 能 | |

转换的三种手法（后面仍会用到）：

| 手法 | 怎么做 | 产出 |
|---|---|---|
| **问法扩增** | 一条事实 → 8–10 种不同问法 | 31 条事实 → **250–310 条** |
| **负样本自动构造** | 换掉数字/地名/节气名/来源 | 等量负样本，**零人工** |
| **干扰项采样** | 每条 query 配 5–10 个非相关事实 | **3,000+ 对**，免费 |

**但请注意**：转换出来的**量**够了，**标签的独立性**没解决。这正是上面三个文本方向失败的原因。

## 三、⭐ 唯一真正能训的模型：果灵识果（视觉侧）

核查 `server/tasks.js` 与 `miniprogram/lib/playground-controller.js` 后发现——**项目里已经有一个真实的、有边界的、可以自采数据的分类任务**：

> `playground` 页面「**果灵识果**」→ `wx.chooseMedia` 拍照 → `POST /api/identify-fruit` → VLM 从候选清单里选

### 3.1 这个任务的全部要素都是真的

| 要素 | 现状 | 来源 |
|---|---|---|
| **任务形态** | **14 类中国本土水果细粒度图像分类** | `fruit-culture.js` 的 4 季 × 水果 = 14 种 |
| **候选类别** | 青梅、桑葚、樱桃、西瓜、桃子、李子、柿子、石榴、秋梨、苹果、枣、砂糖橘、瓯柑、冬枣 | 同上，逐条读出 |
| **当前实现** | qwen-vl 系列 zero-shot，从候选清单里选，输出 `{fruit, confidence}` | `server/tasks.js:125-138` |
| **负类（现成！）** | **35 个域外果物**：榴莲、车厘子、蓝莓、牛油果、菠萝蜜、番石榴、莲雾、红毛丹… | `fruit-scope.js` 的 `OUT_OF_SCOPE_FRUITS` |
| **拒识机制** | 照片模糊或不在清单内 → 返回 `unknown` | `tasks.js` 的 prompt 约束 |
| **客户端链路** | 活的，含隐私确认弹窗、失败提示、结果跳转详情页 | `playground-controller.js:105-140` |

### 3.2 为什么它比文本侧那三个强

**因为它的监督信号是「照片本身」，不是我们自己写的规则。**

- 文本侧的标签：我们自己打的正则 → 模型学我们的规则 → **循环论证**
- 视觉侧的标签：这张图**客观上是**苹果还是瓯柑 → 模型学的是**现实** → **独立信号**

### 3.3 而且它的收益不只是准确率，是工程收益

`playground-controller.js:89-91` 的注释自己承认了问题：

> 「识果链路（拍照→上传→/api/identify-fruit→结果）依赖视觉模型；上游偶发抖动（**qwen-vl 偶尔输出不合法 JSON、瞬时 5xx/超时**）会被服务端降级为 `model_*` 兜底。这里对这类瞬时失败**自动重试两次**，避免把一次抖动当成功能不可用。」

**换成自训练的本地小模型，直接消灭这些复杂度**：

| | 现在（云端 VLM） | 换成自训练小模型 |
|---|---|---|
| 网络 | 必须联网 | **离线可用**（小程序本地跑） |
| 延迟 | 网络往返 + 排队 | **零延迟** |
| 成本 | 每次调用付费 | **零边际成本** |
| 输出 | 偶尔不合法 JSON | **确定性输出** |
| 抖动处理 | 重试 2 次 + `model_*` 降级链 | **整段逻辑可以删掉** |
| 隐私 | 照片上传到云端 | **照片不出设备** |

**这是个比「我训了个模型」好得多的故事**：不是「加了个模型」，是「**把一个不稳定、要联网、要付费、会把用户照片传出去的云端调用，换成了一个自训练的本地模型——更准、更快、更省、更可靠、更保护隐私**」。

### 3.4 难点在哪：细粒度对

14 类里有几对**天然难分**，这正是技术含量的来源：

| 难对 | 为什么难 |
|---|---|
| **砂糖橘 vs 瓯柑** | 都是柑橘属，都是小个头橙色，外观极像 |
| **枣 vs 冬枣** | 同种不同品种，冬枣更大更圆 |
| **青梅 vs 李子** | 同为李属，青熟期几乎一样 |
| **苹果 vs 秋梨** | 圆形、黄绿系，轮廓相近 |
| **柿子 vs 石榴** | 秋季、橙红色系 |

**VLM zero-shot 在「苹果/西瓜」上大概率没问题，但在「砂糖橘 vs 瓯柑」「枣 vs 冬枣」上大概率栽。** 这就是可以量化的增益空间。

## 四、但先别急着训：第一步是测 VLM 基线

**这是整件事的关键决策点。** 训模型之前必须先知道 VLM 现在考多少分：

| VLM 在 14 类上的准确率 | 该怎么办 |
|---|---|
| **> 90%** | ❌ **不用训**。训一个小模型也很难超过，硬做只会得到「不如 baseline」的结果，反而扣分 |
| **70%–90%** | ⚠️ 可以做，但收益主要是**工程收益**（离线/隐私/成本），技术报告要诚实地这么写 |
| **< 70%** | ✅ **值得训**。准确率提升 + 工程收益双重故事，最理想 |

**测基线一天就能做完**：
1. 收集评测集：14 类 × 每类 10 张 = **140 张**（自己拍 + 公开图，注意版权）
2. 加 **35 张域外果物**（测 `unknown` 拒识）
3. 逐张跑 `/api/identify-fruit`，记录 `identified` / `fruit` / `confidence`
4. 算出：**14 类 top-1 准确率** + **unknown 拒识率** + **混淆矩阵**

**这个动作本身就有价值**——即使最后决定不训模型，「**我们评测了 VLM 在 14 类中国本土水果上的细粒度识别能力，发现 X**」也是一份扎实的评测报告，比空口说「用了 VLM」强得多。

## 五、如果决定训：数据方案

### 5.1 数据来源

| 来源 | 量 | 说明 |
|---|---|---|
| **自己拍** | 14 类 × 30–50 张 = **420–700 张** | 最可信，有工作量证明，版权干净。河南本地果园/市场都能拍到 |
| **公开数据集** | Fruit-360 等 | 覆盖苹果/樱桃/西瓜/桃/梨/枣等，但**类别体系对不上**（Fruit-360 是品种级，我们是「中国本土品类」），且**要核对许可证** |
| **域外果物（负类）** | 35 类 × 10 张 = **350 张** | 测 `unknown` 拒识 |

**建议**：主体自己拍（保证类别体系对齐 + 版权干净），公开数据集只作**预训练初始化**，并在报告里如实说明来源与许可证。

### 5.2 数据增强（合法且有效）

旋转、裁剪、色彩抖动、亮度变化、模糊 —— 把 420 张扩到数千张。**这对细粒度识别是标准做法，报告里如实写即可。**

### 5.3 划分

- 训练 70% / 验证 15% / **测试 15%**
- **测试集必须独立**，且要**留出一部分「不同光线/不同背景/不同成熟度」的照片**——否则准确率会虚高

|---|---|---|

## 七、清醒一点：这个任务的边界

我建议你把预期放在这里，避免答辩翻车：

| 判断 | 说明 |
|---|---|
| ✅ **任务真实存在** | 不是造出来的，产品里跑着 |
| ✅ **监督信号独立** | 照片本身是客观的，不是我们写的规则 |
| ✅ **数据能自采** | 不依赖官方数据集（这个赛道本来就不给） |
| ✅ **工程收益明确** | 离线、零延迟、零成本、确定性、隐私 |
| ⚠️ **准确率增益可能有限** | 常见品类 VLM 可能已经做得不错，**必须先测基线** |
| ⚠️ **工作量真实存在** | 自拍 420–700 张 + 标注，3–5 天 |
| ⚠️ **端侧部署有门槛** | 小程序里跑 CNN 需要 wc-tensorflow / ONNX Runtime Web，要验证可行性与包体积 |

**包体积提醒**：主包硬上限 **2 MiB**。一个量化后的 MobileNetV3 约 4–10 MB，**必须走分包或云端推理**。这是要先算清楚的账。

## 八、你真正要的「技术含量」，可能不在训练

说实话——**这个项目最有技术含量的地方，不是「训了什么模型」，而是 `server/tasks.js` 里那套架构**。我读完整个文件后，这里的设计比「训个模型」硬得多：

### 8.1 模型不许自由作答

```js
// An unsupported factual question is never handed to an unconstrained LLM.
if (task === 'ask' && (local.unanswerable || !local.evidenceIds?.length)) {
  return { ...local, latencyMs: Date.now() - started };
}
```

**模型只能从已核验的证据里挑 ID，不能自己写事实。**

```js
// The model chooses evidence. Factual wording stays anchored to reviewed source records.
result = evidence.answerFromEvidence(ids, catalog);
```

输出经过校验：ID 必须在候选集内、数量 1–4、`unanswerable` 必须是布尔值——**任何一条不满足就丢弃模型输出、走本地兜底**。

### 8.2 每个任务都有「诚实降级」，不冒充 AI

| 任务 | 模型不可用时 |
|---|---|
| `identifyFruit` | `拍照识别服务暂不可用，可从链图手动选择水果。`（`local-fallback`） |
| `fruitStory` | 模板化故事骨架，**并明确标注 `mode: 'local-template'`** |
| `sellerInsight` | 数字与状态**由规则给出**，`mode: 'local-rules'` |
| `translate` | `{ translated: false, mode: 'local-fallback' }` |

**「服务挂了就说挂了，不编」——这在 AI 作品里是稀缺品质，评审会认。**

### 8.3 境外内容直接闸门拦截

```js
// 境外果品不交给模型写故事：固定话术在本地拼好，模型没有机会编造他国农事。
if (task === 'fruitStory' && local.outOfScope) return { ...local, latencyMs: Date.now() - started };
```

**内容边界用代码兜底，不靠 prompt 自觉。** 35 个域外果物有明确清单，`fruit-scope.js` 直接分类。

### 8.4 已经有完整的评测体系

32 条标注（含 8 条拒答负样本）+ hit@1/hit@3/MRR/**拒答召回**/误拒率 五个指标 + 两组对照（BM25 vs BM25+约束）。**这是「实验设计」，不是「模型」。而评审看的是实验设计。**

**对「智能文化」这个赛道（开放式赛题、无数据集、100% 专家评审），这套「可控生成 + 可解释 + 诚实降级 + 有评测」的组合，比「我们训了个模型」更对路。**

## 十、答辩怎么讲（修订版）

**不要说**：「我们训了模型」。
**也不要说**：「我们做了 RAG」——这是中档说法。

**要说**（主线是架构，模型是加分项）：

> 「我们的作品是**文化知识问答 + 拍照识果**，服务中国本土果品与农耕文化。
>
> 这类系统最怕三件事：**答错、编造出处、越界**。
>
> **答错**——我们不用自由生成的 LLM。模型只被允许从已核验的证据里挑选 ID，事实措辞锚定在带来源记录上；证据不足就直接拒答，不交给模型发挥。我们在 32 条标注评测集上测了 hit@1、MRR、**拒答召回**，拒答召回达到 1.000。
>
> **编造出处**——31 条文化事实**100% 带来源 ID**，14 个来源全部可核查，每一条都记录了核查日期。
>
> **越界**——35 个域外果物有明确清单，由本地闸门直接拦截，模型没有机会编造他国农事。
>
> **拍照识果**——原本用云端视觉模型，我们实测了它在 14 类中国本土水果上的细粒度表现（**准确率 X%，在砂糖橘/瓯柑、枣/冬枣这些细粒度对上错误率 Y%**），然后训练了一个本地小模型，把准确率提到 Z%，同时**照片不再离开设备、离线可用、零延迟**。
>
> 所有模型不可用的场景都有诚实降级，界面上会明确告诉用户『服务暂不可用』，**我们从不假装 AI 在工作**。」

**为什么这套说法强**：
1. **主线是可控性与诚实性**——这是「智能文化」赛道最该讲的东西
2. **有评测、有基线、有数字**——评审最爱的三件套
3. **模型是「解决问题的手段」而不是「技术炫技」**——本地模型是为了隐私和离线，不是为了刷分
4. **主动暴露边界**——「没数据的方向我们只登记了门槛，没有编造结果」
5. **呼应官方要求**——附录 1 数据、附录 2 模型，一次覆盖

## 十一、一句话回答你的问题

**你说得对——文本侧确实没什么可训的。**

- **三个文本方向（意图分类 / 检索重排 / 引用校验）**：标签全部来自我们自己写的规则，等于「用模型重新实现规则」。**不做。**
- **LLM 微调**：差 15–300 倍，且自生成自评测会失真。**不碰。**
- **唯一真正能训的**：**果灵识果——14 类中国本土水果细粒度图像分类**。任务真实（`/api/identify-fruit` 在跑）、监督信号独立（照片本身是客观的）、数据能自采（420–700 张）、负类现成（35 个域外果物）、收益明确（**离线 + 零延迟 + 零成本 + 隐私 + 删掉重试降级链**）。
- **但第一步不是训模型，是测 VLM 基线**。> 90% 就别训，写评测报告；< 70% 才值得训。
