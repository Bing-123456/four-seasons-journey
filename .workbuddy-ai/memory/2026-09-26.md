## 开发者工具截图配额：真正解法

上一轮判定「只能手动清缓存 + 重启」**不完整**。这次找到了完整的 CLI 解法：

```bash
CLI=/Applications/wechatwebdevtools.app/Contents/MacOS/cli
$CLI cache --clean file --project "$(pwd)"     # 清模拟器文件缓存
pkill -f wechatwebdevtools                     # 必须真的杀掉进程
$CLI auto --project "$(pwd)" --auto-port 9420 --trust-project
```

关键点：
- **自动化端口的参数是 `--auto-port`，不是 `--port`**。`--port` 是 IDE HTTP 服务端口，传它只会得到 `Port is not provided` 或 `must be restarted on port 9420 first`。`--auto-port` 不在 `--help` 里，是从 `core.wxvpkg` 里挖出来的
- `cli quit` **杀不掉** IDE 主进程（端口仍占用）；`osascript -e 'tell application "wechatwebdevtools" to quit'` 会报 -10004 权限违例但实际能退出；最可靠是 `pkill -f wechatwebdevtools`
- **配额计数缓存在运行中的 IDE 进程里**：光删磁盘文件没用，必须重启进程
- 诊断法：连上 automator 后在小程序里跑 `wx.getFileSystemManager().writeFile({filePath: wx.env.USER_DATA_PATH+'/x.txt'})`。若它也报 `the maximum size of the file storage limit is exceeded`，就是配额问题而非截图接口问题
- 模拟器数据在 `~/Library/Application Support/微信开发者工具/<hash>/WeappSimulator/WeappFileSystem/<userhash>/<appid>/{tmp,usr,store}`；`usr/miniprogramLog` 的日志也计入配额

## 技术挖掘分析：冲一等奖/特等奖的缺口

用户问「有没有技术含量高的东西可以再发展一下」。产出一份 `docs/技术挖掘与冲奖方案-2026-09-26.md`。

**核心判断**：问题不是「AI 用得少」，而是**全项目 11 个 AI 接口 100% 是 API 调用，0 个自训练模型**。而官方附件 2 第 3 页明确要求附录提供「关键算法代码、模型文件及相关说明文档」。创新性 25 分最高档要求「全新的 AI 应用模式，具有开创性」——RAG 做得好也只是中档（9–17）。

**关键实测数据（本轮新测出来的）**：
- 主包 **2,083,624 B / 上限 2,097,152 B → 只剩 13,528 B（13.2 KB）**。微信规则：主包 ≤2MB、**单个分包也 ≤2MB**、分包合计 ≤20MB → 端侧模型不能靠塞包解决，只能运行时下载 + 纯 JS 推理，或极小权重进主包
- `catalog.facts` 只有 **31 条**；评测集 **32 条**（10 dev / 22 冻结）；题库 **6 道**。数据量是所有训练方案的最大瓶颈
- 检索基线实测复现：BM25 top3 → hit@1 0.714 / hit@3 1.000 / MRR 0.845 / 拒答召回 0.000；加门控 → 0.857 / 0.857 / 0.857 / 1.000 / 误拒 0.071
- **22 条冻结集上 hit@3 从 1.0 掉到 0.857 = 14 条里错 2 条**，样本量不足以支撑任何训练决策 → 第一件事应该是扩评测集，不是训练
- 43 个测试文件 / 374 处 `test()`；服务端运行时只依赖 `ws`

**被低估的既有资产**（都没进技术叙事）：
