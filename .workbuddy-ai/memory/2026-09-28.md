### 发现并修复：评测数据引用错位（重要教训）
- 现象：C 组误拒率异常偏高（0.143），看起来像模型问题

- 修复后：误拒率 0.143 → **0.000**，检索层 hit@1 0.857 → **0.929**
- 数据集升版 `culture-seed-2026-09-28-v2`（在 `labelStatus` 里写明修正内容）
- **`scripts/check-project.js` 新增检查**：评测集的 `placeId` / `relevantFactIds` 必须存在于 catalog，否则 `npm run check` 报错。已验证能拦下（临时改坏→报错→恢复→校验和一致）

**教训**：**评测数据引用错位会静默污染实验结论，而且它伪装成模型失败。** 修完模型指标"变好了"——这正是必须先证明「是数据错了」再改，而不是反过来调模型的原因。

### 自己写的指标 bug（也记一下）
第一版 `summarise()` 给 C 组传了 `judges: null`，裁判没跑，`verdict` 被填成 `'answered'`，于是「忠实度」永远算成 0——C 组答案明明是核验资料原文。

## L3 稠密检索 + L4 RRF：建成并实测，得到一个反直觉负结果

### 先探明 API（不探明就写代码容易白干）
| 模型 | 端点 | 维度 | 结果 |
|---|---|---|---|
| `text-embedding-v4` | OpenAI 兼容 `/compatible-mode/v1/embeddings` | 1024 | ✓ |
| **`qwen3-vl-embedding`** | **原生多模态** `/api/v1/services/embeddings/multimodal-embedding/multimodal-embedding` | **2560** | ✓ |
| `qwen3-vl-rerank` | 原生 `/api/v1/services/rerank/text-rerank/text-rerank` | 返回 `relevance_score` | ✓ 区分度好 |
| `gte-rerank-v2` | 同上 | — | ⚠️ **实测仍可调用**（此前记的「已下线」要修正为「已公告下线、实测可用、但不应依赖」） |

**坑（文档没写）**：`qwen3-vl-embedding` **单次 contents ≤ 20 条**，31 条一次提交报 `InvalidParameter: batch size is invalid`。已按 20 分批。
**注意**：`qwen3-vl-embedding` **不在 OpenAI 兼容端点上**（404），必须走原生端点。
**选它的理由**：文本/图片同一语义空间 → L8 跨模态检索可复用同一索引。

### 实验设计：2×3 因子（排序器 × 是否用人工标注）
动机是回答评审必然追问的一句：「你们 hit@1 0.929，多少来自算法、多少来自人工标注？」

| 组 | hit@1 | hit@3 | MRR | 拒答召回 |
|---|---|---|---|---|
| 纯 BM25（无标注） | 0.714 | 1.000 | 0.845 | 0.000 |
| **纯稠密（无标注）** | **0.929** | 1.000 | **0.964** | 0.000 |
| BM25+稠密 等权 RRF（无标注） | **0.786** ↓ | 1.000 | 0.893 | 0.000 |
| BM25 + 闸门 | 0.929 | 0.929 | 0.929 | 1.000 |
| 稠密 + 闸门 | 0.929 | 0.929 | 0.929 | 1.000 |
| BM25+稠密 RRF + 闸门 | 0.929 | 0.929 | 0.929 | 1.000 |

### 三条发现
1. **语义模型可替代人工标注做召回**：纯稠密零标注 hit@1 0.929 = 带标注 BM25，MRR 0.964 全场最高。→ 那套 13×22 标注在「找对事实」上并非不可替代。
2. **等权 RRF 是负收益**（0.786 < 0.929）。因为 BM25（0.714）明显弱于稠密（0.929），等权融合让弱排序器给强排序器的正确结果投反对票。**通用原则：融合前先度量各排序器单独质量，质量不对等时要加权或不用融合。**
3. **闸门之后候选池恒为 1 条**（32 条全部：0 条 11 个、1 条 21 个，平均 1.00，最大 1）。→ **闸门即检索**，排序层在闸门之后完全冗余。这解释了为什么带闸门的三组数字完全相同。已固化成测试。

### 未调参的纪律
在 dev 拆分上扫了 9 个权重，但 **dev 只有 7 条可答问题，单条翻转 = 0.143 跳变**，扫出的「最优」是噪声 → **不采用任何调参权重**，报告未调参的等权结果。数据集明确规定 evaluation 冻结、不据测试结果调优门限。

### 架构结论（本轮不切换）
- 路线 A（现状）：闸门即检索 —— 可控可审计，但强依赖人工标注
- 路线 B（备选）：稠密召回 top-K + 闸门只判「能否答」—— 零标注、泛化好，但候选从 1 变 K，需重跑完整消融验证忠实度
- **切换会改变整条管线行为，必须重跑完整消融才能下结论，所以先备齐依据**

## 第三轮（16:00–17:20）语音输入改为**双引擎**：插件已授权 + 服务端兜底

**起因**：用户反馈「用微信原生的比较好」，随后自己去后台把插件加了下来（截图确认），要求验证。
我明确说过「网页打开 ≠ 插件已授权」，于是实测。

**实测插件可用**（`scripts/probe-plugin-wiring.js`，需开发者工具自动化端口 9420）：
`requirePlugin('WechatSI')` 拿到对象，`getRecordRecognitionManager` / `textToSpeech` 都是 function，
控制台零 error ⇒ **后台授权确实生效了**。

**探出一个会静默失效的真坑（本轮最有价值的产出）**：

```
onStart / onStop / onError / onRecognize
  → 都是**可写数据属性**，出厂值都是空函数 `function(e){}`
manager.start 源码
  → setCallback("onStop", this.onStop) …（**读属性当前值**再注册）
```

⇒ **回调必须用赋值式 `manager.onStop = fn`**；调用式 `manager.onStop(fn)` 是**静默空转**，
回调永远不来、界面表现为「点了没反应」。官方**文档的方法表**写成「onStop callback」会误导，
**以官方示例代码为准**。

我最初的 `bindOnce` 写的正是调用式 —— 差点发出去。**为什么差点漏掉**：模拟器不支持录音，
两种写法探测都是「零回调」，只有把 `start` 的源码 dump 出来才看清。

**对照（两条链路注册方式不同，别互相套用）**：
- 插件 `recordRecoManager` → **赋值式**，赋值即替换，天然幂等，不需要去重；
- `wx.getRecorderManager()` → **注册器式** `onStop(cb)`，**会叠加监听器** → 必须 `WeakMap` 只绑一次。

**顺带纠正一处旧错误**：本文档此前写「插件录音上限 30s」——**错的**。官方文档明确
`duration` 默认 **60000**、**最大 60000**；30s 只是官方示例代码里传的值。

**改动**：`miniprogram/lib/speech-input.js`（重写为双引擎：`probePlugin` / `createPluginEngine`

## 第四轮（17:30）复核服务端 ASR 口径，纠正一处夸大表述

用户问「服务端用的是什么方案/模型/API」，顺带把数字核了一遍。

实算（16 kHz / 24 kbps mp3 ≈ 3 KB/s，base64 ×1.33 ≈ 4 KB/s）：

| 录音 | base64 后 | 全局 16384 |
|---|---|---|
| 3 s | ≈ 12 KB | 通过 |
| 4 s | ≈ 16 KB | 勉强通过 |
| 5 s | ≈ 20 KB | **413** |

**教训**：写「必然失败」这类断言前，先把数量级算一遍。**「每次都挂」和「超过 X 就挂」是两个结论，
后者才可证伪、才有用。**
